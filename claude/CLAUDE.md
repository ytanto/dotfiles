# CLAUDE.md

このファイルは、コードを扱う際のClaude Code (claude.ai/code) への指針を提供します。

## ガイドライン

- 指示者に対しては日本語で回答すること
- 質問に対して勝手に行動を開始しないこと。まずは回答すること。
- 自動テストが導入されている場合は、
  - コードの修正後は必要に応じてテストコードを追加すること
  - コードの修正後は必ず自動テストを実行し、全てのテストがパスすることを確認すること
  - テストが失敗した場合は、修正を行い再度テストを実行すること
- コードの修正後は不要・利用されていないファイルやコードを削除すること
- 常にMVPを意識し、必要な機能のみを実装すること
- **後方互換が崩れる変更・既存機能の挙動が変わる変更を行う前は必ず指示者に確認すること**
  - 既存の条件分岐 / 権限制御 / 動的ロジック / API 仕様 / props・emit などを削除・置換するときは、変更後の挙動と影響範囲を明示して GO サインを取る
  - 「見た目を寄せる」「リファクタする」等の依頼でも、内部仕様が変わるなら確認する。スタイル統合の依頼で機能仕様を勝手に削除・固定値化しない
- 開発やレビューでリポジトリを横断する場合は、対象リポジトリの CLAUDE.md や rules を明示的に読むこと
  - これらは実行ディレクトリのツリー外にあると自動では読み込まれないため、横断時は能動的に参照する
- GitHubを参照する場合は、ghコマンドを優先して利用すること
- コミットメッセージに「レビュー対応」等、コードから読み取れないコンテキストの情報を含めないこと
  - あくまでコードをどういった目的・背景・内容を変更したかをメッセージとすること
- サーバーサイドの実装は必ずTDDで行うこと
- ライブラリ（ランタイム・CLI ツール）の管理には mise を優先して利用すること
  - インストールや実行は `mise use` / `mise install` / `mise exec` を使い、バージョンはプロジェクト直下の `mise.toml` に記載する
  - 全体設定 `~/.config/mise/config.toml` は `~/dotfiles/mise/config.toml` へのシンボリックリンク。編集するときは実体（dotfiles 側）を触ること
  - Homebrew との併用は可。mise で扱えないものは brew を使ってよいが、まず mise を検討する
- コードコメントは「What（何をしているか）」ではなく「Why（なぜそうしたか）」を書くこと
  - コードを読めば分かる処理内容はコメントにせず、意図・背景・制約・トレードオフなどコードから読み取れないことを残す
  - コメントで補う前に、命名やリファクタで意図が伝わる自己説明的なコードを優先すること
  - 他モジュールや他レイヤー・利用側（クラス名・メソッド名・ファイル名、フロントのUI概念・ラベルなど）を名指しで参照するコメントは書かないこと
    - ドキュメント上の密結合が生まれ、参照先の改名・移動・削除でコメントが陳腐化する
    - コメントはそのコードが属する層・ファイル単体で完結する説明にとどめる（例: サーバは「所属施設を持たない」など自層の事実で書き、フロントの表示ラベルやグルーピングに言及しない）

## ツール結果の信頼性

- ツール拒否・rerun・割り込み・`/compact` の直後は、それ以前のツール出力を「未確認」とみなし、作業を続ける前にクリーンなコマンドで事実（`git log`/`diff`, `ls`, `wc` 等）を取り直して基準を作り直すこと
- `tool_use` を出したら、本物の `tool_result` ブロックが返るまで結果を書かないこと（想像で結果を先読みしない）
- Read の結果が `wc`/`ls`/`git` と食い違う、パス/SHA/ファイルが疑わしい等のときは、別手段でもう一度取得して突き合わせてから判断すること（1回の結果だけで「再現性が確定した」と決めない）

## worktree セッションではシェルコマンドを分割する

- worktree で作業しているセッションでは、シェルコマンドを**素の単独コマンド**に分割して実行すること。`for` ループや、worktree 外のパスを参照/リダイレクトする複合コマンドは、worktree 隔離ガードに「worktree 内に収まることを静的に検証できない」として**拒否される**（承認を求めるのではなく実行自体を断られる）
- 具体的な回避:
  - `git add <明示パス>` と `git commit` は別々の呼び出しにする（`git add -A` も対象が静的に定まらないため明示パスを使う）
  - コミット本文・PR 本文・Issue 本文は **worktree 内のファイル**に書き出し、`-F <file>` / `--body-file <file>` で渡す。scratchpad（worktree 外）のファイルを直接渡すと弾かれるので、必要なら worktree 内へ `cp` してから使う
  - 複数ファイルを確認する場合もループにせず1ファイルずつ読む

## 承認を求められた原因を取り違えない

- コマンドが承認待ちになったら、まず `~/.claude/settings.json` の **`permissions.ask` ルール**を疑うこと。`defaultMode` は `auto` で、許可リストに無い通常のコマンド（`git commit` / `docker compose` / `gh pr create` 等）は無承認で通る。**「許可リストが足りない」という診断はほぼ誤り**で、許可リストへの追加を提案しても解決しない
- `~/.claude/settings.json` は `~/dotfiles/claude/settings.json` へのシンボリックリンク。**設定を直すときは実体（dotfiles 側）を編集する**。リンクが外れて実体が二重化していると、dotfiles 側の変更が効かないまま古い設定が生き続けるので、挙動が設定と食い違うときはリンクの有無を確認する

## advisor ツールのフォールバック

- `advisor` ツールが `unavailable`（利用不可）を返し「二度と使うな」と指示された場合は、代替として **別エージェントを `model: fable` で新規起動** し、アドバイザー役（敵対的レビュアー）として使うこと
  - `subagent_type: "fork"` は自分のモデル（Opus）を引き継ぐため Fable にはならない。Fable を使うには **非 fork の agent に `model: fable` を指定** する
  - 新規エージェントは会話文脈を持たないため、必要な材料（差分ファイルのパス・対象リポジトリ・自分が出した結論や findings）をプロンプトに明示して渡す
  - 指示は「追従せず敵対的に検証し、REFUTE すべきは REFUTE。見落としも探す」とし、各項目に確度を付けさせる（実装は Opus・レビューは Fable の役割分担に沿う）
