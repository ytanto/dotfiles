着手からテスト証跡までを 1 本で走り切る。**起動時に全体計画を提示して一度だけ承認を取り、以降は判断が要る場面だけ止まる。**
段階ごとに逐一「進めていいですか」とは聞かない（それを聞かない代わりに①の計画提示を丁寧にやる）。

## 全体の流れ

```
/dev-flow
  ⓪ デザインドキュメントを確保（無ければ plan-design-doc を必ず通す）
  ① 計画提示・一括承認（worktree を切るか／UI レーンに入るかをここで決める）
  ② worktree（①で選んだときだけ）
  ③ 実装（Figma あり → リポの figma-implement / Figma なし・叩き台が要る → ux-build）
  ④ UX 自己検査（UI レーンのみ・コミット前・ローカル画面）
  ⑤ /simplify → 品質ゲート → commit → push
  ⑥ PR 本文
  ⑦ PR 作成 → デザイナーへ依頼（UI レーンのみ）
  ⑧ デザイナーレビュー（UI レーンのみ・回答待ちで中断。⑨と並走）
  ⑨ CI レビュー対応（指摘 0 まで）
  ⑩ テスト実施 + エビデンス
  ⑪ 完了報告
```

各段は前段の出力を入力にする。**⑧⑨の両方が終わるまで⑩に進まない**（実装が変われば撮り直しになる）。
⑪で終わりではない。**worktree を切った場合はユーザーの完了指示を待って片付ける**（⑪の直後に勝手に消さない）。

### 開発のどの段階で呼ばれても成り立つ

`/dev-flow` は最初から走らせるとは限らない。「実装は済んでいて PR だけ」「PR はあるからレビュー対応とテストだけ」「デザイナーの回答が来たので続き」のように**途中から呼ばれる**。そのため、**起動時にまず現在地を判定し、①の計画で「どの段から始めるか」を明示して承認を取る。** 各段は「入力」が揃っていれば前段を自分で通していなくても始められるように書いてある。

現在地の判定（読み取り専用。上から順に見る。結果を①の計画に載せる）:

| 見るもの | 手段 | 分かること |
|---|---|---|
| worktree の中か | `git rev-parse --git-dir` と `--git-common-dir` の比較 | worktree のルールを適用するか |
| PR | `gh pr view --json number,url,baseRefName,isDraft,body,comments` | ⑥⑦が済んでいるか。**base は PR があれば `baseRefName`、無ければ①の 3 で規約から決める**。規約違反の base（hotfix が開発ブランチ向き等）は停止条件。**draft なら自動レビューは走っていない** → ⑦で `gh pr ready` にしてから⑨へ |
| Issue 番号 | ブランチ名の `#n` → PR 本文の関連 Issue → 無ければ聞く | ⓪の対象 |
| Issue とデザインドキュメント | `gh issue view <n> --comments` | ⓪が済んでいるか（コメントにドキュメント書式があるか。本文からリンクされた先も見る）。**Figma の有無**は Issue 本文のデザインリンクで判定し、今回の変更がそのノードに描かれているかまで見る。「対応方針」に ux-build の指示があれば「叩き台が要る」寄り（gh-create-issue が Figma の無い UI 変更に書く） |
| ブランチと作業ツリー | `git status -sb`（ahead 表示で未 push が分かる）、`git log <base>..HEAD --oneline`、`git diff --name-only <base>...HEAD` | 未コミット変更・未 push コミットの有無。**UI 変更の有無**は diff に画面系ファイルがあるか。新規の画面・コンポーネント・ルート・状態の追加が無ければ「軽微」候補 |
| ③ 実装が済んでいるか | ユーザーの申告 + diff を⓪の決定事項・成功条件に突き合わせる | 欠けがあれば③を差分で通す（diff があることと完了は別） |
| デザイナー依頼（UI レーン） | PR コメントに Part 1 / 2 / 3 があるか、返信があるか、**コメント投稿後に画面系ファイルへのコミットがあるか** | ⑦⑧の状態: 未依頼 / 回答待ち / 回答済み・未反映 / 反映済み・再確認待ち / 終了。投稿後に画面が変わっていれば④の差分再検査が要る |
| CI レビュー | `gh-review-feedback` の正本の取得手順（未 resolve スレッドは GraphQL）、最新レビューの結論、bot のレビューが 1 件も無いか・失敗コメントがあるか | ⑨の状態。**bot のレビューが無い／失敗していれば、⑨の最初に `@claude` にフルレビューを依頼して起動する**（正本はレビューがある前提で始まるため、起動は dev-flow の責務） |
| テスト証跡 | PR **本文**のテスト節のチェックが埋まり、`user-attachments/assets` の動画 URL が本文にあるか | ⑩が済んでいるか。**コメント側の画像は④の成果物であって⑩ではない** |

判定のルール:

- **飛ばしてよいのは「済んでいる」と確認できた段だけ。** 確認できない段は済んでいない扱いにする（「たぶん済んでいる」で飛ばさない）。品質ゲートのように再実行が安いものは迷わず再実行する
- **⓪と①は途中から呼ばれても必ず行う。** ③以降が済んでいる場合の⓪は、実装から逆算した決定事項・成功条件を Issue コメントに記録するのが目的（plan-design-doc の書式は使うが質問は最小）。①の「実コードに突き合わせる」は「実装が決定事項どおりか」の確認に読み替える
- **前段の成果物が無いまま後段に来た場合は、その段の入力を作ってから始める。** 例: PR はあるが本文の「テスト実施」節が画面操作の手順になっていない → ⑩の前に⑥を通す。UI レーンなのに Part 1 / 2 / 3 のコメントが無い → ⑧の前に④⑦を通す
- **既に済んでいる段の成果物は上書きしない。** PR 本文を直すときは変更内容とテスト節に限り、他の節と添付 URL は保持する（gh-pr-description の「ライブ本文を取り直す」に従う）。それ以外の節を変えるならユーザーに確認する。コメントとエビデンスは追記
- **push 済みのコミットに対して `/simplify` を回さない。** 以降の修正で触る範囲にだけ効かせる。既存コミットがある場合、③の「コミットはまだしない」は「追加分をまだコミットしない」と読む
- 実行計画には「開始する段」「飛ばす段とその根拠（確認したもの）」を書く

### UI レーン

UI 変更の扱いは①で次の 4 つに分ける。UI レーンに入るのは「Figma なし・叩き台が要る」だけで、ux-build と ux-probe はセットで回し、その結果をデザイナーがレビューして確認する段（⑧）を持つ。

| ①での判定 | ③ 実装 | ④ 自己検査 | ⑦⑧ デザイナー |
|---|---|---|---|
| UI 変更なし | 通常実装 | 飛ばす | 飛ばす |
| **Figma あり** | 対象リポの `figma-implement` スキルで組む（無ければリポの rules に従う） | 飛ばす（Figma との突合は figma-implement が持つ。⑥のキャプチャは載せる） | 飛ばす |
| **Figma なし・叩き台が要る** | `ux-build` | `ux-build` 6.5〜7 + `ux-probe` + `a11y-check` | 実施 |
| **Figma なし・軽微（ux-build 不要）** | 通常実装 | 飛ばす | 飛ばす |

「軽微」の定義: **変更の全項目が ux-build Step 5 の 🔧（DS 定義・Figma 由来か DS 準拠の既存パターン・原則のどれかから方向が一意に決まり、影響がその画面で閉じる）に収まる**こと。例: 文言の修正、項目の並び替え、既存コンポーネントのプロップ変更、Figma 由来の既存パターンの再利用。**新しい画面・状態・導線・情報構成を増やす、または揃える先が開発先行の画面（弱い見本）**なら軽微ではない。迷ったら「叩き台が要る」に倒して①で提示し、ユーザーに選ばせる。軽微でも⑥の変更後キャプチャは載せる。

## 委譲先スキルと、呼び出せないという制約

この skill は**手順を複製せず、各段の正本を読んでその通りに実行する**。

| 段 | 正本 | `Skill` ツールで起動できるか |
|---|---|---|
| ⓪ | `crosslog:plan-design-doc`、`crosslog:gh-create-issue` | ○ |
| ② | `worktree` | ○（手元に無ければ①で「今のチェックアウト」を選ぶ） |
| ③ ④ | `crosslog:ux-build`、`crosslog:ux-probe`、`crosslog:a11y-check` | ○ |
| ⑤ | `simplify`（組み込み） | ○ |
| ⑤ | `crosslog:qa-lint-and-push` | **×** |
| ⑥ | `crosslog:gh-pr-description` | ○ |
| ⑦ | `crosslog:gh-create-pr` | ○ |
| ⑨ | `crosslog:gh-review-feedback` | **×** |
| ⑩ | `crosslog:test-run-with-evidence` | **×** |

**× は `disable-model-invocation: true` のため `Skill` ツールから起動できない**（`Skill <name> cannot be used with Skill tool` が返る）。
→ **× の段は SKILL.md を `Read` して、書かれた手順を自分でインライン実行する。** 実体は次で解決する（バージョン付きの `cache/` ではなく `marketplaces/` を読む）。

```bash
ls -d ~/.claude/plugins/marketplaces/crosslog-plugins/plugins/crosslog/skills/<name> 2>/dev/null \
  || find ~/.claude/plugins -type d -name <name> | head -1
```

- **手順をこのファイルに書き写さない。** 正本が更新されても追従できなくなる。毎回 `Read` する
- ○ の段は `Skill` ツールで普通に起動してよい。○× は frontmatter の `disable-model-invocation` で決まるので、起動に失敗したら `Read` に切り替える
- リポジトリ固有の値（ブランチ規約・品質ゲートのコマンド・worktree の事情）は `references/repos/<リポジトリ名>.md` にある。**対象リポジトリの `.claude/rules/` と CLAUDE.md が正本**で、references はその要約に過ぎない。無いリポジトリは正本だけで進める

## ⓪ デザインドキュメントを確保する

**Issue とデザインドキュメントが揃っていない限り①に進まない。** Issue に「対応方針」が書かれていても、それが正しいとは限らず、粒度も足りないことが多い。

| 状態 | やること |
|---|---|
| **Issue 未作成** | `plan-design-doc` で設計を固める → 成果物の置き場は「Issue コメント」を選ぶ → plan-design-doc が `gh-create-issue` で起票（本文は what / why のみ）してからデザインドキュメントをコメントに投稿する。gh-create-issue は「要件を詰めてから起票しますか？」を必ず一度聞くので、詰め済みなら「このまま下書きへ」を選ぶ |
| **Issue はあるがデザインドキュメントが無い** | `plan-design-doc` を回し、その Issue のコメントに投稿する。「対応方針」欄が埋まっていても、下の書式の粒度に達していなければ「無い」扱い |
| **両方ある** | ドキュメントを読んで①へ。「決定事項」と「未決事項」をそのまま①の計画に引く |

「ある」の判定: Issue のコメント（または本文からリンクされた先）に、plan-design-doc の書式（ゴール / 非ゴール / 決定事項 / 前提 / エッジケース / 影響範囲 / 成功条件 / 未決事項）で書かれたものがある。

**「未決事項（実装前に要決定）」が残っている間は①に進まない。** plan-design-doc の質問で潰すか、決める人に投げて回答を待つ（途中から呼ばれた場合の例外は次段落）。

**実装済みで途中から呼ばれた場合も⓪は行う。** ドキュメントが無ければ plan-design-doc で作るが、目的は「実装から逆算した決定事項・成功条件を記録する」ことに変わる（書式は使うが質問は最小）。未決事項が既に実装した内容に影響しないなら残作業（⑤以降）を止めない。

## ① 計画を提示して一括承認を取る

**ここが唯一の承認ポイント。** 以下を確定してユーザーに提示し、OK をもらってから先へ進む。

確定すべきこと:

1. **対象リポジトリ**と作業ディレクトリ
2. **Issue 番号**（⓪で必ず存在する）
3. **ブランチ名とベースブランチ** — **対象リポジトリの `.claude/rules/git-workflow.md`（無ければ CLAUDE.md と既存 PR の `baseRefName`）を必ず読む。規約はリポジトリごとに違う**（リリース側のブランチが `main` のリポと `master` のリポがある）。要約は `references/repos/`。他リポの規約を流用しない。hotfix を開発ブランチに出すとリリース経路がずれる。どちらか判断できないときは聞く
4. **worktree を切るか、今のチェックアウトで進めるか** — ユーザーに選ばせる。推奨は worktree だが、慣れていない人は今のチェックアウトでよい。今のチェックアウトを選んだら、作業ツリーが clean で目的のベースブランチにいることを確認してからブランチを切る
5. **UI 変更の扱い** — 「UI 変更なし / Figma あり / Figma なし・叩き台が要る / Figma なし・軽微」のどれかを決める（「UI レーン」の表）。UI レーンに入るのは「Figma なし・叩き台が要る」だけ
   - **「Figma あり」＝今回の変更内容が Figma の対象ノードに描かれている。** Issue にデザインリンクがあっても、今回の変更が Figma に描かれていなければ（既存画面の文言修正で Figma が未更新など）Figma なし側で扱う
   - **Figma あり のときは対象ノードの URL（node-id 付き）を握る。** `figma-implement` の入力になる。Issue には Figma のトップ URL しか書かれないことが多いので、ここで確定する。webapp は対象アプリ（connect / report）も
   - Figma あり は軽微でも `figma-implement` を通す（正本が「小さい画面でも棚卸しを飛ばさない」と定めている）。棚卸しで不足コンポーネントが出て規模が膨らんだら、①の実装スコープを再提示する
6. **UI レーンのとき**: 操作してよい範囲（保存・削除系を押してよいか）、締切と検出の受け皿、レビューを頼むデザイナー。ux-probe の Step 0 が要求する前提で、ここで握らないと④で止まる
7. **実装スコープ** — ⓪のデザインドキュメントの「決定事項」を引く
8. **⑤の品質ゲートの中身** — 実際に走らせるコマンド（対象リポの `.claude/rules/commands.md`、無ければ CLAUDE.md。要約は `references/repos/`）
9. **⑩のテスト実施環境** — どのアプリをどこで起動して撮るか

### デザインドキュメントを実コードに突き合わせる

⓪のドキュメントが前提にしている挙動が実際に成り立つかを、**最小の実験で確かめてから**先へ進む。ここを飛ばすと、実装した後で設計に戻ることになる。

次のいずれかなら、**②へ進まず⓪の `plan-design-doc` に戻してドキュメントを書き直す**（dev-flow はそこで中断し、固まってから①をやり直す）:

- 前提にしている挙動が、実際には成り立たない
- ドキュメントどおり直しても、Issue が解決しない
- 実装の選択肢が複数あり、どれを採るかで影響範囲・後方互換・運用コストが変わるのに、決定事項に無い
- 仕様変更（ユーザーに見える挙動の変更）を伴うのに、その是非が書かれていない

**誤った方針を Issue に残さない。** 設計に戻したら、Issue 側のドキュメントも併せて書き換える（次に読む人が同じ誤りを踏むため）。

提示のしかた:

```
## 実行計画
- 開始する段: <⓪〜⑪>。飛ばす段: <段と、済んでいると確認したもの>
- リポジトリ: <repo> / ブランチ: <branch>（base: <base>）/ worktree: 切る or 切らない
- Issue: #<番号> <タイトル>（デザインドキュメント: <コメント URL>）
- UI: 変更なし / Figma あり（対象ノード URL: <node-id 付き>）/ Figma なし・叩き台が要る（→ UI レーン。デザイナー: <名前>）/ Figma なし・軽微
- 実装: <2〜4行>
- 品質ゲート: <実際のコマンド>
- テスト: <どの画面をどう操作して撮るか。PR本文のテスト項目が確定するのは⑥なので、ここでは方針でよい>

このまま<開始する段>〜⑪を走り切ります。途中で止まるのは「判断が要る場面」（下記）のときだけです。
```

**「判断が要る場面」を計画と一緒に明示する。** これを先に言っておくことで、以降黙って進めることが許される。

## 途中で止まってユーザーに相談する場面

これ以外では止まらない。**止まると決めたら、選択肢と推奨を添えて聞く**（「どうしますか」だけで投げない）。

| 場面 | なぜ止まるか |
|---|---|
| **後方互換が崩れる / 既存機能の挙動が変わる**変更に行き着いた | 条件分岐・権限制御・API 仕様・props/emit の削除や置換は GO サインが要る |
| **レビュー指摘に反論がある**、または指摘の意図が読めない | 誤った指摘をそのまま取り込むと実装が劣化する |
| **ベースブランチ／ブランチ命名が規約のどちらとも判断できない、または既存 PR の base が規約と違う** | リリース経路を間違えると巻き戻しが高くつく。既存 PR の base 変更（`gh pr edit --base`）は副作用なので確認してから |
| **品質ゲートが落ちて、直し方に複数の選択肢がある** | 単純な修正なら黙って直してよい。設計判断を含むなら聞く |
| **マージ先とコンフリクトした** | このフローのスコープ外。`crosslog:gh-resolve-conflicts`（明示起動のみ。使うなら SKILL.md を `Read` して従う）に委ねるため、ここで止めて案内する |
| **テスト項目が実装と食い違っている** | 項目が間違っているのか実装が間違っているのかは、人が決める |
| **不可逆・外向きの操作**（リリース、本番データ変更、外部への送信） | このフローには含まれない。要求されたら止める |
| **デザインドキュメントの前提が実コードと食い違っていた** | 方針が誤っている可能性がある。⓪に戻す判断が要る |
| **デザイナーの回答が既存 DS や画面横断の一貫性を変える内容だった** | この PR で閉じるか、別 Issue に切るかは人が決める |
| **⑩でブランチ切り替え・アプリ起動・migration・seed 投入・データ削除が要る** | `test-run-with-evidence` の正本が実行前の承認を要求している。①で環境を決めていても、データ調達の承認は残る |
| **⑨がラウンド上限に達しても収束しない** | 残った指摘を列挙して人に渡す。回し続けても収束しない |
| **②のベースラインが赤い** | 自分の変更前から落ちている。進めるか先に調べるかは人が決める |
| **Figma あり の③で、スコープ表の確定と「要確認」Comment Note の解消** | `figma-implement` の正本が要求する停止点。ノードが複数画面を含むことが多く、どこまで実装するかは人が決める |

止まったあとは、**回答を得たらその場から再開する**（①からやり直さない）。

## ② worktree を作って進入する（①で選んだときだけ）

**正本**: `worktree` スキル。作成・セットアップ・作業ルール・掃除はすべてそちらに従う。

- 今のチェックアウトで進めると①で選んだ場合はこの段を飛ばし、ベースブランチを `git fetch` してから作業ブランチを切るだけにする。手元に `worktree` スキルが無い人も同じ
- **worktree の有無に関わらず、コードを触る前にベースラインを取る。** 依存を入れたら品質ゲート（重ければ lint と型チェックだけ）を 1 回回し、後で落ちたときに自分の変更起因かを切り分けられるようにする。赤なら止まる（停止条件）
- worktree を切ったときだけ効く決まり（シェルコマンドの分割・Read / Edit のパスを worktree 配下に切り替える・⑪の片付け）は `worktree` スキルの正本を読む。**このファイルには写さない**
- フロントとサーバの両方を変えるタスクでは `EnterWorktree` が使えない。`worktree` スキルの「複数リポジトリを触るタスク」に従い、理由をユーザーに伝えてから手動作成に切り替える

## ③ 実装

このスキルは実装手順そのものを規定しない。**対象リポジトリの CLAUDE.md と `.claude/rules/` に従う。** このフロー固有の注意だけ:

- **①で確かめた前提が、実装中に崩れたら止まる。** そのまま辻褄を合わせに行かず、①の「⓪に戻す」判断へ
- **設計ドキュメントの「要件」が実コードと食い違うことがある。** 設計時に想定した挙動が、既に別の経路で実現されている／そもそも起きない、というケース。この場合は止まらず、**現状の挙動を実コードで確かめて、現状維持が正しいなら要件のほうを直して進む**（そのうえで Issue 側のドキュメントも直す）
- **作業中に本題と無関係な問題（別の脆弱性・秘密情報の混入など）を見つけても、そこで作業を止めない。** 記録して先へ進み、⑪の報告に含める
- 実装が終わったら**不要になったファイル・コードを消す**。⑤の前にやる（消し忘れがレビュー指摘になって⑨が 1 周増える）
- **コミットはまだしない。** ④⑤を通してからコミットする

### UI 変更の組み方（①で決めたパターンごと）

- **Figma あり**: 対象リポの `figma-implement` スキルを起動して組む（Figma の読み方・トークン変換・突合はそのスキルが持つ。無いリポは rules と CLAUDE.md に従う）
- **Figma なし・叩き台が要る（UI レーン）**: `crosslog:ux-build` の Step 0〜5。既存 DS に寄せる → 原則で組む → 状態を網羅 → 文言 → 仕分け。出力は叩き台と**デザイナー確認リスト**（先に決めたい / 決まらなくても進められる / 目を通してほしい仮決め）。迷った箇所は仮決めして進め、リストに積む。確認待ちで手を止めない
- **Figma なし・軽微**: 通常実装。変更の全項目が ux-build Step 5 の 🔧 に収まっているかを③の終わりに確かめ、収まらなければ「叩き台が要る」に切り替える（①の判定を訂正してユーザーに伝える）

## ④ UX 自己検査（UI レーンのみ・コミット前）

**正本**: `crosslog:ux-build` の Step 6.5〜7（エビデンス撮影 + `crosslog:ux-probe`）。`crosslog:a11y-check` を併走させる。**ローカル起動の画面で回してよい**（ux-probe は本番での実行を禁じているだけで、ローカルを禁じていない。a11y-check はローカル URL を明示的に受け付ける）。ux-probe の Step 0 には①で握った項目のほかに正規導線から入る・既知仕様ログを読む・前回レポートの有無・保存先などの前提があるので、正本どおりに揃えてから走る。

- **実装直後・コミット前に回す。** 🔧 の検出はその場で直し、⑤のゲートに整理後のコードを通す。コミットが 1 本で済み、デザイナーへの依頼も早まる
- 撮影と probe は同じ工程で回す（どちらも実画面を動かす）。エビデンスは網羅ではなく**判断に効く最小枚数**
- 検出の仕分け: 🔧 その場で直す / 🎨 デザイナー確認 / ⚙️ 開発内で仕様確認 / ❓ 裏が取れない。**意図的な逸脱が検出されるのは正しいので潰さない**
- **保存先はこのフローでは PR コメント 1 本に固定する。** 委譲先の既定（ux-probe と a11y-check は Issue コメント、ux-build は実装依頼スレッドまたは PR 説明欄）と食い違うので、ux-probe Step 0 の「保存先」はここで「⑦で作る PR のコメント」と確定させ、委譲先の既定に引っ張られない
- 成果物は⑦で貼るために手元にまとめる: **Part 1: ux-build**（挙動＋エビデンス → 確認リスト → 意図的逸脱 → 新バリアント候補。レビュー緊急度フラグ含む）、**Part 2: ux-probe**（レポート書式のまま）、**Part 3: a11y-check**（同じコメントの末尾）。書式は ux-build の「出力は 1 か所に、スキルごとにセクションを分ける」と a11y-check の併走時の規約に従う

## ⑤ /simplify → 品質ゲート → コミット → push

⑧からの修正で戻ってくる合流点でもある。**ゲートを通してから push する。** ⑨の修正は `gh-review-feedback` の正本が自前で持つ検証 → commit → push の手順に従い、⑤へは戻らない（ゲートのコマンドは⑤と同じ）。⑨で実装を大きく直したときは、commit 前に `/simplify` だけ回してよい。

⑧由来の修正で戻ってきたときは、**この段は commit までで止め、push は⑨のラウンド境界で行う**（⑨が待機中でなければそのまま push してよい）。

### まず `/simplify` を回す（コミット前）

**正本**: 組み込みの `simplify` スキル。変更したコードの再利用・単純化・効率・抽象度のズレを見て、**修正を適用する**。

- **必ずコミット前に回す。** push した後に回すと「整理だけのコミット」が余分に増え、レビュー時の差分も読みにくくなる
- **これはバグを探すスキルではない**（品質のみ）。バグ観点は⑨の CI レビューに任せる
- **適用された差分は自分で確認する。** 意図した挙動が変わっていないかを `git diff` で見る。挙動が変わる整理が混ざっていたら戻す（「後方互換が崩れる変更」は停止条件に該当する）

### 品質ゲート → コミット → push

**正本**: `crosslog:qa-lint-and-push` の SKILL.md を `Read` して従う。リポジトリ別のゲートは対象リポの `.claude/rules/commands.md`、無ければ CLAUDE.md（要約は `references/repos/`）。

- コンテナの中で走るゲートは、**コンテナにどのコードが載っているか**を先に確認する。worktree で作業しているときは特に（`worktree` スキルの `references/docker-backend.md`。リポ別の事情は `references/repos/`）
- ⑨の周回を減らしたいなら、push 前に組み込みの `code-review` を 1 回だけ回し、**正しさに関わる指摘だけ**直してよい（承認は不要。`qa-review-loop` の軽量版で、収束までは回さない）
- 「デザインドキュメントの決定事項が全部実装されているか、スコープ外を触っていないか」は code-review では判定できない。push 前に⓪のドキュメントと自分で照合する
- **ゲートがコードを書き換えることがある**（`rubocop -a`、prettier / eslint の `--fix` など）。ゲートを通したら `git diff` を見直してからコミットする。意図しない書き換えが混ざっていたら戻す
- **落ちたら直して再実行する。** 通るまで先へ進まない。直し方に選択肢があるときだけ止まって聞く
- コミットメッセージは対象リポの規約に従う。**「レビュー対応」などコードから読み取れない文脈を書かない**（⑨でのコミットも同じ）

## ⑥ PR 本文を書く

**正本**: `crosslog:gh-pr-description`。

- **「テスト実施 / 動作確認手順」節は⑩の入力になる。** ここで書いた項目をそのまま⑩で実施して録画する。だから**画面を操作して確認できる手順**で書く。ユニットテストの結果列挙にしない
- **テスト節に `curl` や SQL を書かない。** API 直叩き・DB 確認は rspec が担保する領域で、テスト節は画面操作だけにする
- **レアな異常系の改善を「よくあるケース」に読める書き方で載せない。** 書くなら発生条件を明記する
- リポジトリの `.github/PULL_REQUEST_TEMPLATE.md` に準拠する
- **テスト項目は⓪のデザインドキュメントと対応付ける。** 「成功条件」は必ず 1 行ずつテスト項目に引き当て、対応の無い成功条件があればここで気づく（⑩で撮る項目がドキュメントから漏れない）。エッジケースは代表的なものだけにする（正本が「細かいエッジケースを網羅しない」と定めている）。対応表は PR に書かず手元で持つ
- **UI 変更があるなら Figma の有無に関わらず変更後の画面キャプチャを「変更内容」に載せる**（gh-pr-description の規約）。UI レーンでは④で撮った画像を再利用し、④を飛ばすパターンは `test-playwright` の `references/recording.md` に従って撮る
- **UI レーン**: 本文には「デザイナー確認中」の一文だけ置く。コメントへのリンクは⑦で投稿してから書き戻す。確認リスト本体は本文に書かない（書式が衝突し、再検査のたびに本文が膨らむ）

## ⑦ PR を作成する → デザイナーへ依頼する

**正本**: `crosslog:gh-create-pr`。ベースブランチは①で確定したものを渡す。**PR は open のまま作る**（draft にしない）。

- 作成後、**PR の URL と番号を控える**。⑧⑨⑩で使う
- 途中から入って既存 PR が draft だったら `gh pr ready` にする（ready_for_review で自動レビューが走る）

### UI レーン: すぐに依頼する

PR を作ったら**すぐ**、④の Part 1 / Part 2 / Part 3 を **PR コメント 1 本**に貼り、①で決めたデザイナーに依頼する。ここが UI レーンで一番早く出せる依頼点で、CI レビューの結果を待たない。

- 投稿したらコメントの URL を PR 本文の「デザイナー確認中」の一文に書き戻す（本文はライブの内容を取り直してから編集する）
- 「何を確認したいのか・回答によって何が変わるのか」が揃っていれば、確認は一往復で済む
- 🎨 に仕分けた検出は Part 2 の「デザイナーに確認したいこと」に置いたままでよい。Part 1 に書き直して二重にしない

## ⑧ デザイナーレビュー（UI レーンのみ・回答待ちで中断）

⑦のコメントを材料に、デザイナーが叩き台を検収する。**dev-flow はここで中断し、回答を待つ。** 待ち時間に⑨の CI レビュー対応を進める（コードの指摘は UI の判断と独立）。

- **回答の反映**: 修正 → ④を**差分だけ再検査** → ⑤（commit まで）→ ⑨のラウンド境界で push → 再依頼
  - 「差分だけ」の定義: 変更した画面・状態に走査を絞り、ux-probe の走査カバレッジ表で未実施にした項目に理由を書く。前回比の列は付ける。Part 1 は前回へのリンクと更新点だけで、無理に新しい確認事項を作らない
  - 再依頼は元のコメントに追記したうえで、メンション付きの短い新規コメントを出す（編集だけでは通知が飛ばない可能性がある）
  - **⑨のラウンド途中に push しない。** ⑧由来の修正は⑨のラウンド境界（返信・resolve 後、`@claude` 通知前）で取り込み、同じ通知で再レビューさせる。途中で push すると bot の再レビューと既対応判定が乱れる
- **回答で確定した仕様は⓪のデザインドキュメント（Issue コメント）の決定事項に追記する。** ux-probe の Step 0 はそこを読むので、書き戻さないと次回の再検査が同じ検出を出す。プロダクト横断で効く挙動なら既知仕様ログへの追記をデザイナーに依頼する（ux-probe の共有ログの規約）
- **終了条件**: 「先に決めたい」項目に回答が揃い、🎨 が残っていない（または次の改修へ送ると合意した）。人が介在するのでラウンド上限は置かない
- 回答が既存 DS や画面横断の一貫性を変える内容なら、影響範囲を示して相談する（停止条件）

## ⑨ CI レビュー対応を指摘 0 まで回す

**正本**: `crosslog:gh-review-feedback` の SKILL.md を `Read` して従う。**この段のループ構造は正本が持っている**（未 resolve スレッド取得 → 対応計画 → 修正 → push → 返信・resolve → `@claude` 通知 → 再レビュー待機 → 次ラウンド）。

このフロー固有の注意:

- **bot のレビューがまだ 1 件も無い、または失敗コメントで終わっているときは、最初に `@claude` にフルレビューを依頼して起動する。** 正本はレビューが既にある前提で始まる
- **1 ラウンドの締めは「スレッド外の通常コメントで `@claude` に通知する」まで**（文言は正本に従う）。スレッド内の返信には `@claude` を入れないので、それだけでは bot は再レビューを回さない
- **自動レビューは PR の open / ready_for_review でしか走らない。** push しても再レビューは来ないので、`@claude` 通知が唯一の再実行手段
- **通知への返答が「対応確認」で済まされることがある。** bot は軽微な差分を diff 直読で返してよい設定になっているため、フルレビューが欲しいラウンドは通知文に「再レビュー」「フルレビュー」と明示する。レビューが不自然に短いときも同じ文言で再実行させる
- **指摘が事実か実コードで確かめてから直す。** bot の指摘は外れることがある。再現や `grep` で裏を取り、外れなら根拠を返信して resolve する（修正しない）。同調の言い回しで済ませない
- **指摘をそのまま受け入れる限り、承認を求めず進む。** 止まるのは「途中で止まって相談する場面」の表に該当したときだけ。正本のラウンド上限（5）に達しても収束しなければ、残った指摘を列挙して止まる
- **指摘 0 の判定**: 未 resolve スレッドが 0 件、かつ最新のレビューが新規指摘なしで完了していること。「返信したから 0」ではない
- **UI レーン**: 指摘対応で画面が変わったら④を差分再検査し、⑧のコメントに補足を出す。そこで出た 🔧 修正は次のラウンドの修正に含め、正本の commit → push で出す（⑤には戻らない）

### インラインコメントは最後まで読む

レビュー bot のインラインコメントは 1 スレッドに複数の指摘を入れてくる。本文を途中で切って読むと、1 点だけ直して「対応しました」と返してしまい、次のラウンドで突き返される。取得は truncate せず全文を読む。

### 同じ欠陥クラスは自分で横断する

レビュー bot は指摘が不在形（「〜が漏れている」）のとき、同じ欠陥クラスの他インスタンスを横断で洗い出す。**指摘された箇所を直したら、同じパターンが他に無いかを自分で `grep` してから返信する。** 繰り返し踏んだ例:

- プロップを配線したが**片方の分岐にだけ**入れた（compact と通常表示、新規作成用と編集用など）
- 同じ判定が複数ファイルに重複していて、指摘された 1 つだけ直した
- 供給側の戻り値を消したのに、消費者側／テスト側の参照が残った

### 直したら「外すと落ちるか」を確かめる

テストを足したときは、**対応する実装の句を実際に外して、そのケースだけが落ちること**を確認する。「テストを書いた」と「テストが実装を守っている」は別。

- 否定アサーション（`not.toHaveBeenCalled()`）を `waitFor` で包まない。失敗理由が読めなくなる
- **ablation でファイルを戻すとき `git checkout -- <file>` を使わない。** その回で入れた未コミットの修正まで巻き戻る。退避してから戻すか、Edit で元に戻す
- 配線漏れは、プロップを optional にしていると `tsc` もテストも通ってしまう。**中継するコンポーネントの側を必須にする**と、外した瞬間に型エラーになる

## ⑩ テストを実施してエビデンスを PR に貼る

**正本**: `crosslog:test-run-with-evidence` の SKILL.md を `Read` して従う（`references/` も同じディレクトリにある）。ブラウザ操作と録画の実行環境は `crosslog:test-playwright` が正本。

- **⑧⑨の両方が終わってから撮る。** 実装が変わると撮り直しになる。途中から「⑩だけ」を頼まれた場合も、現在地判定表の⑧⑨の行で終了を確認してから始める
- 入力は⑥で書いたテスト項目。**項目と実装が食い違っていたら止まって聞く**（どちらを直すかは人が決める）
- ④のエビデンスとは目的が違う。こちらは「通ったことの証明」で網羅と検証（`waitFor`）が要る
- 録画は **Playwright MCP の `page.screencast`**。webm で撮って mp4 に変換し、**納品するのは mp4 だけ**
- **スクリプトを渡す `filename` はプロジェクトルートか `<repo>/.playwright-mcp/` のみ**（playwright-mcp のファイルアクセス制限）。録画の出力先はこの制約を受けないので scratchpad でよい。`.playwright-mcp/` が gitignore されているか `git check-ignore` で確認し、必要なら `.git/info/exclude` に足す（**リポジトリの `.gitignore` は勝手に変えない**）

```
- 自分で決めた判断: <決めたこと・理由・外れたときのコスト。無ければ「なし」>
- 本題と無関係に見つけた問題: <あれば>

worktree: <パス>。**「完了」と言ってもらえれば片付けます**（今は残しています）
```

- **完了の主張には新鮮な証拠を添える。** 「通るはず」「直したので大丈夫」は書かない。最後の変更の後に実際に走らせた結果だけを書く
- UI レーンでない場合は UI レーンの行を、worktree を切らなかった場合は worktree の行を「該当なし」にする
- **worktree を勝手に消さない。** ユーザーがその worktree で画面を触って確認する時間が要る。片付けは `worktree` スキルに従い、`git status` が dirty なら消さず差分を見せて確認する

## 注意

- **①の承認を取らずに②以降を始めない。** 「走り切ってよい」という許可は①の 1 回で得るものであって、暗黙には得られない
- **段を飛ばさない。** 特に⑤（品質ゲート）を飛ばして push すると、⑨で lint 由来の指摘が積まれて余計に周回する
- **途中から呼ばれたら「開発のどの段階で呼ばれても成り立つ」の判定表で現在地を決める。** 飛ばしてよいのは済んでいると確認できた段だけ
- **1 回の dev-flow に収まらない規模のことがある。** 複数リポジトリ・複数 PR に分かれる施策では、①で**全体の分解を示したうえで「今回はどこまでか」を決める**。依存順（サーバ追加 → クライアント切替 → 締め）とリリース順（対の PR は同時）は別物なので、両方を①で明示する
- **コミット本文・PR 本文はファイルに書いて `-F` / `--body-file` で渡し、使い終わったら消す。** worktree のときはファイルを worktree 内に置く（`worktree` スキルの `references/shell-commands.md`）
- **このスキルは実装の良し悪しを判断しない。** 自己レビューを厚くしたいなら、③の後に `crosslog:qa-review-loop` を別途回す（このフローには含めていない。⑨の CI レビューと役割が重なるため）
- 終了時に、**作った worktree 以外に副作用が残っていない**ことを確認する
