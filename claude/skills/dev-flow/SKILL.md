着手からテスト証跡までを1本で走り切る。**起動時に全体計画を提示して一度だけ承認を取り、以降は判断が要る場面だけ止まる。**
段階ごとに逐一「進めていいですか」とは聞かない（それを聞かない代わりに①の計画提示を丁寧にやる）。

## 全体の流れ

```
/dev-flow → ① 計画提示・一括承認 → ② worktree → ③ 実装 → ④ 品質ゲート+push
          → ⑤ PR本文 → ⑥ PR作成 → ⑦ レビュー対応(指摘0まで) → ⑧ テスト実施+証跡 → ⑨ 完了報告
                ↓ 設計が未確定なら
            /crosslog:plan-design-doc（ここで中断。固まってから①へ戻る）
```

各段は前段の出力を入力にする。**⑦が指摘0になるまで⑧に進まない**（レビューで実装が変われば、撮り直しになる）。
⑨で終わりではない。**worktree はユーザーの完了指示を待って片付ける**（⑨の直後に勝手に消さない）。

## 委譲先スキルと、呼び出せないという制約

この skill は**手順を複製せず、各段の正本を読んでその通りに実行する**。正本は以下。

| 段 | 正本 | `Skill` ツールで起動できるか |
|---|---|---|
| ① | `crosslog:plan-design-doc`（設計が未確定のときだけ） | ○ |
| ② | `worktree`（dotfiles） | ○ |
| ④ | `crosslog:qa-lint-and-push` | **×** |
| ⑤ | `crosslog:gh-pr-description` | ○ |
| ⑥ | `crosslog:gh-create-pr` | ○ |
| ⑦ | `crosslog:gh-review-feedback` | **×** |
| ⑧ | `crosslog:test-run-with-evidence` | **×** |

**× の3つは `disable-model-invocation: true` のため `Skill` ツールから起動できない**
（`Skill <name> cannot be used with Skill tool` が返る。`pr-review` が `code-review` で踏んだのと同じ制約）。

→ **× の段は SKILL.md を `Read` して、書かれた手順を自分でインライン実行する。**
プラグインスキルの実体は下記。バージョン付きの `cache/` ではなく `marketplaces/` を読む（cache は複数版が同居していてどれが有効か紛らわしい）。

```
~/.claude/plugins/marketplaces/crosslog-plugins/plugins/crosslog/skills/<name>/SKILL.md
```

- **手順をこのファイルに書き写さない。** 正本が更新されても追従できなくなる。毎回 `Read` する
- ○ の段は `Skill` ツールで普通に起動してよい

## ① 計画を提示して一括承認を取る

**ここが唯一の承認ポイント。** 以下を確定してユーザーに提示し、OK をもらってから②へ進む。

確定すべきこと:

1. **対象リポジトリ**と作業ディレクトリ
2. **Issue 番号**（引数で渡されていなければ聞く。無いなら「Issue なし」と明示する）
3. **ブランチ名とベースブランチ** — リポジトリの `.claude/rules/git-workflow.md` を読んで規約に合わせる。webapp では:
   - 通常開発 `feature/{app}/#{Issue番号}-{タイトル}` → base `develop`
   - 緊急バグ修正 `hotfix/{app}/#{Issue番号}-{タイトル}` → base `main`
   - **どちらか迷ったら聞く。** hotfix を develop に出すと、リリース経路がずれる
4. **実装スコープ** — 何をどう変えるかの要約。Issue 本文に「対応方針」があればそれを引く
5. **④の品質ゲートの中身** — 実際に走らせるコマンド（下の「④」参照）
6. **⑧のテスト実施環境** — どのアプリをどこで起動して撮るか
7. **設計が実装に落ちる粒度で確定しているか** — 下記「設計が固まっていないときは実装に入らない」

### 設計が固まっていないときは実装に入らない

**Issue に「対応方針」が書かれていても、それが正しいとは限らない。** ①でその方針を実コードに突き合わせ、
**成立するかどうかを最小の実験で確かめてから**②へ進む。ここを飛ばすと、worktree を作って実装した後で
設計に戻ることになる。

確認して次のいずれかなら、**②へ進まず `/crosslog:plan-design-doc` に切り替える**（dev-flow はそこで中断し、
設計が固まってから改めて①から始める）:

- 方針が前提にしている挙動が、実際には成り立たない
- 方針どおり直しても、Issue が解決しない
- 実装の選択肢が複数あり、どれを採るかで影響範囲・後方互換・運用コストが変わる
- 仕様変更（ユーザーに見える挙動の変更）を伴うのに、その是非が Issue に書かれていない

**誤った方針を残したまま実装しない。** 設計に切り替えたら、Issue の対応方針も併せて書き換える
（次に読む人が同じ誤りを踏むため）。

提示のしかた:

```
## 実行計画
- リポジトリ: <repo> / ブランチ: <branch>（base: <base>）
- Issue: #<番号> <タイトル>
- 実装: <2〜4行>
- 品質ゲート: <実際のコマンド>
- テスト: <どの画面をどう操作して撮るか。PR本文のテスト項目が確定するのは⑤なので、ここでは方針でよい>

このまま①〜⑨を走り切ります。途中で止まるのは「判断が要る場面」（下記）のときだけです。
```

**「判断が要る場面」を計画と一緒に明示する。** これを先に言っておくことで、以降黙って進めることが許される。

## 途中で止まってユーザーに相談する場面

これ以外では止まらない。**止まると決めたら、選択肢と推奨を添えて聞く**（「どうしますか」だけで投げない）。

| 場面 | なぜ止まるか |
|---|---|
| **後方互換が崩れる / 既存機能の挙動が変わる**変更に行き着いた | ユーザーの明示ルール。条件分岐・権限制御・API 仕様・props/emit の削除や置換は GO サインが要る |
| **レビュー指摘に反論がある**、または指摘の意図が読めない | 誤った指摘をそのまま取り込むと実装が劣化する |
| **ベースブランチ／ブランチ命名が規約のどちらとも判断できない** | リリース経路を間違えると巻き戻しが高くつく |
| **品質ゲートが落ちて、直し方に複数の選択肢がある** | 単純な修正なら黙って直してよい。設計判断を含むなら聞く |
| **マージ先とコンフリクトした** | このフローのスコープ外。`/crosslog:gh-resolve-conflicts` に委ねるため、ここで止めて案内する |
| **テスト項目が実装と食い違っている** | 項目が間違っているのか実装が間違っているのかは、人が決める |
| **不可逆・外向きの操作**（リリース、本番データ変更、外部への送信） | このフローには含まれない。要求されたら止める |
| **Issue の対応方針が実コードと食い違っていた** | 方針が誤っている可能性がある。実装ではなく設計に戻す判断が要る（上記「設計が固まっていないときは実装に入らない」） |

止まったあとは、**回答を得たらその場から再開する**（①からやり直さない）。

## ② worktree を作って進入する

`worktree` スキルの方針に従う。要点だけ再掲する（詳細は正本を読む）:

- **Claude Code のネイティブ機能を使う**（`claude --worktree <名前>` / `EnterWorktree`）。自作スクリプトは使わない
- 進入直後に **`mise trust`**（webapp / crosslog-front）
- **依存インストールは `run_in_background: true`** で走らせ、完了を待たずに③へ進む
- **back系（Docker あり）は worktree 側で `docker compose up` しない**

### worktree 内でのシェルコマンドの書き方（事故る）

worktree セッションでは**素の単独コマンドに分割する**。`for` ループや worktree 外のパスを参照する複合コマンドは、
隔離ガードに「worktree 内に収まることを静的に検証できない」として**拒否される**（承認を求められるのではなく実行自体を断られる）。

- `git add <明示パス>` と `git commit` は**別々の呼び出し**にする（`git add -A` も対象が静的に定まらないので使わない）
- コミット本文・PR 本文は **worktree 内のファイル**に書き出して `-F <file>` / `--body-file <file>` で渡す。
  scratchpad（worktree 外）のファイルを直接渡すと弾かれる。必要なら worktree 内へ `cp` してから使う
- 複数ファイルの確認もループにせず1ファイルずつ

## ③ 実装

このスキルは実装手順そのものを規定しない。リポジトリの CLAUDE.md と `.claude/rules/` に従う。
このフロー固有の注意だけ:

- **①で確かめた前提が、実装中に崩れたら止まる。** 実装しながら「この方針では直らない」と分かることがある。
  そのまま辻褄を合わせに行かず、①の「設計が固まっていないときは実装に入らない」に戻る
- **サーバーサイドは TDD**（ユーザーの明示ルール）。テストを書いてから実装する
- 実装が終わったら**不要になったファイル・コードを消す**。④の前にやる（消し忘れがレビュー指摘になって⑦が1周増える）
- **コミットはまだしない。** ④の品質ゲートを通してからコミットする

## ④ 品質ゲート → コミット → push

**正本**: `crosslog:qa-lint-and-push` の SKILL.md を `Read` して従う。

リポジトリ別のゲート（正本に書かれていなければこれを使う）:

| リポジトリ | コマンド |
|---|---|
| webapp / connect | `pnpm --filter connect run check:all` |
| webapp / report | `pnpm --filter report-front run check:all` |
| webapp / video | `pnpm --filter video-front run format` と `check-types`（`check:all` は無い） |
| baas-platform ほか back系 | rspec + rubocop（リポジトリの CLAUDE.md に従う） |

- **`<app>` は package.json の `name`**（`connect` / `report-front` / `video-front`）であってディレクトリ名ではない
- **落ちたら直して再実行する。** 通るまで先へ進まない。直し方に選択肢があるときだけ止まって聞く
- コミットメッセージは `<prefix>: <内容> (#<Issue番号>)`。
  **「レビュー対応」などコードから読み取れない文脈を書かない**（⑦でのコミットも同じ）

## ⑤ PR 本文を書く

**正本**: `crosslog:gh-pr-description`（`Skill` ツールで起動してよい）。

このフロー固有の注意:

- **「テスト実施 / 動作確認手順」節は⑧の入力になる。** ここで書いた項目をそのまま⑧で実施して録画する。
  だから**画面を操作して確認できる手順**で書く。ユニットテストの結果列挙にしない
- **テスト節に `curl` や SQL を書かない。** API 直叩き・DB 確認は rspec が担保する領域で、テスト節は画面操作だけにする
- **レアな異常系の改善を「よくあるケース」に読める書き方で載せない。** 書くなら発生条件を明記する
- リポジトリの `.github/PULL_REQUEST_TEMPLATE.md` に準拠する

---

## ⑥ PR を作成する

**正本**: `crosslog:gh-create-pr`（`Skill` ツールで起動してよい）。ベースブランチは①で確定したものを渡す。

- 作成後、**PR の URL と番号を控える**。⑦⑧で使う
- draft にするかは①で決めておく（実機確認が済んでいない段階なら draft が無難）

---

## ⑦ レビュー対応を指摘0まで回す

**正本**: `crosslog:gh-review-feedback` の SKILL.md を `Read` して従う。**この段のループ構造は正本が持っている**（未resolveスレッド取得 → 対応計画 → 修正 → push → 返信・resolve → `@claude` 通知 → 再レビュー待機 → 次ラウンド）。

このフロー固有の注意:

- **1ラウンドの締めは「スレッド外の通常コメント `@claude レビュー対応完了しました`」まで。**
  スレッド内の返信だけでは bot は再レビューを回さない。ここを忘れるとループが止まったまま待ち続けることになる
- **自動レビューが途中で終わることがある**（SDK がバックグラウンドタスクを待たず success 終了する既知の問題）。
  レビューが不自然に短い・明らかに見ていない範囲があるときは、`@claude このPRをフルレビューして` で再実行させる
- **指摘をそのまま受け入れる限り、承認を求めず進む。** 止まるのは「途中で止まって相談する場面」の表に該当したときだけ
- **指摘0の判定**: 未resolve スレッドが0件、かつ最新のレビューが新規指摘なしで完了していること。
  「返信したから0」ではない。**resolve まで済んでいることを確認する**

## ⑧ テストを実施してエビデンスを PR に貼る

**正本**: `crosslog:test-run-with-evidence` の SKILL.md を `Read` して従う。`references/playwright-recipes.md` も同じディレクトリにある。

このフロー固有の注意:

- **⑦が指摘0になってから撮る。** レビューで実装が変わると撮り直しになる
- 入力は⑤で書いたテスト項目。**項目と実装が食い違っていたら止まって聞く**（どちらを直すかは人が決める）
- 録画は **Playwright MCP の `page.screencast`**。webm で撮って mp4 に変換し、**納品するのは mp4 だけ**（webm は残さない）
- **`filename` の出力先はプロジェクトルートか `<repo>/.playwright-mcp/` のみ。** scratchpad は使えない。
  `.playwright-mcp/` が gitignore されているか `git check-ignore` で確認し、必要なら `.git/info/exclude` に足す
  （**リポジトリの `.gitignore` は勝手に変えない**）

## ⑨ 完了報告

```
## /dev-flow 完了

- PR: <URL>（base: <base>）
- レビュー: <N>ラウンドで指摘0
- テスト: <M>項目実施・エビデンス <K>本を PR に添付
- 品質ゲート: <コマンド> 通過
- 途中で判断を仰いだ点: <あれば1行ずつ。無ければ「なし」>

worktree: <パス>。**「完了」と言ってもらえれば片付けます**（今は残しています）
```

- **worktree を勝手に消さない。** ユーザーがその worktree で画面を触って確認する時間が要る
- 片付けの手順は `worktree` スキルに従う。`git status` が dirty なら消さず、差分を見せて確認する

## 注意

- **①の承認を取らずに②以降を始めない。** 「走り切ってよい」という許可は①の1回で得るものであって、暗黙には得られない
- **段を飛ばさない。** 特に④（品質ゲート）を飛ばして push すると、⑦で lint 由来の指摘が積まれて余計に周回する
- **途中から呼ばれることがある。** 「PR は作ってあるからレビュー対応とテストだけ」のような場合は、
  現在地を `git branch` / `gh pr view` で判定し、**該当する段から始める**。①の計画提示はその場合も行う（範囲を明示するため）
- **worktree に入ったら、Read / Grep のパスをすべて worktree 配下に切り替える。**
  進入前の会話に残っている main checkout の絶対パスを使い続けると別ツリーを読む
- **このスキルは実装の良し悪しを判断しない。** 自己レビューを厚くしたいなら、③の後に `/crosslog:qa-review-loop` を別途回す
  （このフローには含めていない。⑦の CI レビューと役割が重なるため）
- 終了時に、**作った worktree 以外に副作用が残っていない**ことを確認する
