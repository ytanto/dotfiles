---
name: pr-review
description: PR の URL / 番号を渡されたら、worktree でそのブランチに切り替え → code-review で所見を出す → qa-review-loop の検証専用モードで所見を敵対的に裏取り → 統合報告、までを一気通貫で行う。「このPRレビューして」「PR見て」「レビューして裏取りまでして」等、PR の URL や番号とともにレビューを頼まれたら使う。コード修正は一切行わない読み取り専用のフロー。
---

PR を渡されたら、**隔離された worktree でレビューし、所見を敵対的に検証してから報告する**までを1本で回す。
**コードは一切修正しない。** 修正を求められたらこのスキルの範囲外で、検証結果を渡したうえで別途指示を取る。

## 全体の流れ

```
PR URL → ① PR情報取得 → ② worktree 切り替え → ③ /code-review → ④ qa-review-loop(検証専用) → ⑤ 統合報告
                                                                          ⑥ 後片付け（ユーザーが「レビュー完了」と言ったら）
```

各段は前段の出力を入力にする。**②を飛ばして main checkout でレビューしない**（作業中のツリーを汚す・別ブランチを読んでしまう）。
**⑤は「全エージェントの回収」と「sweep を含む全所見の3レンズ通過」の両方が済んでから1回だけ出す**
（詳細は「⑤へ進む前に『全エージェント回収』と『全所見の検証完了』の両方を満たす」）。
⑤で終わりではない。**⑥はユーザーの完了指示を待って実行する**（報告直後に勝手に消さない。ユーザーがその worktree で画面を触って確認する時間が要る）。

---

## ① PR 情報を取得し「変更の意図」を確定する

```bash
gh pr view <番号> --repo <owner/repo> --json number,title,body,headRefName,baseRefName,state,additions,deletions,changedFiles
```

- `body` から **変更の意図** を抽出する。後段の検証エージェントはこれが無いと**意図的な変更をバグとして誤検出する**
- 同時に **「チームが意図的に選んだ設計判断」**（PR本文が「これは仕様」と書いている点）を切り出しておく。これも後段に必須
- `baseRefName` を控える。**変更前コードとの比較基準**として④で使う最重要の入力

## ② worktree に切り替える

`worktree` スキルがあればその方針に従う。無い場合の最小手順:

```bash
git -C <repo> fetch origin '<headRefName>'
git -C <repo> worktree add .claude/worktrees/<slug> -b '<headRefName>' 'origin/<headRefName>'
```
→ `EnterWorktree` に **`path` を渡して**進入する。

- **`EnterWorktree` の `name` は使わない**。新規ブランチを切ってしまい、既存のリモートブランチをチェックアウトできない
- 既に同ブランチの worktree があれば（`git worktree list`）作らず再利用する。同一ブランチは2つの worktree に同時チェックアウトできない
- **進入直後に `mise trust` を実行する**（mise 管理のリポジトリ = crosslog-front / webapp）。`worktree` スキルの必須セットアップで、読み取り専用フローでも省略しない。実測では、これを飛ばしたまま進んで後続の `git` / `gh` 実行時に `mise ERROR ... not trusted` を踏んだ
- **依存インストール（`yarn install` 等）は `run_in_background` で走らせる。** レビュー自体は Read / Grep / `git` / `gh` しか使わないので待つ必要はないが、**レビュー結果を受けてユーザーがその worktree で実際に画面を触って確認する**ため、環境は整えておく。バックグラウンドなので③④の待ち時間には乗らない
  - 完了を待たずに③へ進む。レビュー中に lint / test / dev サーバーを起動することは無いので、インストールの成否がレビューをブロックすることもない
- **`.worktreeinclude` を読み、列挙された git 管理外ファイルを main checkout からコピーする。**
  `.worktreeinclude` は `EnterWorktree` が worktree を「作る」ときにしか処理されず、既存のリモートブランチを
  チェックアウトするための手動 `git worktree add` では効かない（`name` は新規ブランチを切ってしまうので使えない）。
  コピーを飛ばすと `.env` の無い worktree ができる。依存インストールと同じ理由（レビュー後にユーザーがその
  worktree で画面を触る）で必須。レビュー自体には不要だが、後から「起動できない」と気付くと確認が止まる。
  ```bash
  # リポジトリルートの .worktreeinclude を読み、存在するものだけコピー
  cd <main checkout> && grep -v '^#' .worktreeinclude | grep -v '^$' | while read -r p; do
    for f in $p; do [ -e "$f" ] && mkdir -p "<worktree>/$(dirname "$f")" && cp "$f" "<worktree>/$f"; done
  done
  ```
  `ios/` `android/` は絶対パスを含む生成物なのでコピー対象外（必要なら worktree 内で `expo prebuild`）
- 進入以降、**Read / Grep のパスはすべて worktree 配下に切り替える**。進入前の会話に残っている main checkout の絶対パスを使い続けると別ツリーを読む
- 手動 `git worktree add` した worktree は**セッション終了時に自動削除されない**。⑤の報告でパスを伝え、ユーザーの完了指示を受けて⑥で削除する

## ③ /code-review で所見を出す

`Skill` で `code-review` を PR URL 付きで起動する。出力は `file` / `line` / `summary` / `failure_scenario` の JSON 配列。

- **`code-review` は `disable-model-invocation` のため `Skill` ツールからは起動できない**（`Skill code-review cannot be used with Skill tool` が返る）。ユーザーが `/code-review` と打った時しか動かないので、このフローでは**最初から自前でレビューパネルを組む**
  - 変更ファイルを観点別に分割し、**独立した Agent を並列起動**する（例: 正しさ / 規約・配置 / テスト網羅 / 周辺への影響）。各エージェントには PR の変更意図と `baseRefName` を渡し、`file` / `line` / `summary` / `failure_scenario` の JSON で返させる
  - 同名の `review` スキルは GitHub PR 向けだが**散文レビューを返す**ので、④に渡す構造化所見としては使いにくい。使うなら出力形式を明示して上書きする

- ここでは**所見を絞り込まない**。recall 重視で出させ、取捨は④に委ねる
- **lint / test は実行しない。** 判断はすべてコードを読んで行う

### エージェント起動プロンプトに必ず入れる（③④共通）

観点別レビュアーも④の検証レンズも、下記3点を**プロンプト本文に明記する**。書かないと毎回同じ事故が起きる。

- **結果の返し方**: 末尾に「調査結果は `SendMessage({to: "main", message: "<JSON>"})` で main に送ること。**最終テキストを書くだけでは main に届かない。**message の中身は JSON そのもの（前後に説明文なし）。所見ゼロなら `[]` を送る」と書く。
  これが無いと、エージェントは完了しても **idle 通知だけが返り最終テキストが main に届かない**。実測では14エージェント全員がそうなり、1件ずつ `SendMessage` で催促する往復が発生した。
  **明記しても催促は要ると想定しておく**（別の実測では、明記した8エージェント全員が自発的には送らず、1体は3回目の催促でようやく応答した）
- **実行禁止の明示**: 「コードは修正しない。`lint` / `test` / ビルドは実行しない。使うのは Read / Grep / `git`（`show`/`diff`/`log`）/ `gh` だけ」と書く。
  スキル本文に書いてあってもサブエージェントには伝わらない。実測では規約担当が独断で `npx eslint` / `npx stylelint` を実行した
- **リリース順序を所見にしない指示**: 「対となるバックエンド PR が未マージ・未デプロイであることを理由にした
  『フロント先行リリースで壊れる』という所見は出さないこと。対の PR は必ず同時にリリースされる前提でよい」と書く。
  詳細は⑤の「所見にしないもの」参照。書かないと周辺影響担当が毎回これを High で挙げてくる

### 規約チェックで必ず踏むこと（ここが一番漏れる）

- **CLAUDE.md が名指しで参照しているドキュメントを必ず辿って読む。** 自動注入される `.claude/rules/*.md` だけで済ませない。
  CLAUDE.md に「ファイル配置は `docs/policies/directory-structure.md` を必ず読むこと」のような指示があれば、その実ファイルを開く。
  実測では、これを飛ばしたせいで「feature 内に `utils/` を作らない」という明文規約への違反を1巡目で見落とした
- **lint の baseline / suppression ファイルを開く**（`eslint-suppressions.json` 等）。
  変更ファイルがそこに登録されていないか確認する。**登録済みのファイルに新規コードを足すと、規約違反が恒久的に不可視になる**。
  実測では `unicorn/filename-case` が baseline で握り潰されており、`yarn lint` は緑のまま通っていた
- **リネーム・移動・新規ファイルが差分にあれば、配置規約とファイル名規約を必ず1件ずつ照合する**

## ④ qa-review-loop を検証専用モードで回す

`Skill` で `qa-review-loop` を起動し、**修正なしの検証専用モード**であることを明示する。渡す入力:

1. ③の所見リスト（`file:line` / 主張 / 失敗シナリオ / 提案された修正）
2. ①の変更の意図
3. ①の「チームが意図的に選んだ設計判断」
4. ②の比較基準（`baseRefName`）

### qa-review-loop に上乗せする必須ルール

素の qa-review-loop はこれらを必須にしていない。**毎回明示的に指示する。**

- ③の「**エージェント起動プロンプトに必ず入れる（③④共通）**」を、④の全レンズ・sweep にもそのまま適用する

- **所見1件につき3レンズを並列**（1エージェントに束ねない。束ねると結論が相互汚染する）

  | レンズ | 役割 |
  |---|---|
  | **legacy** | `git show <base>:<path>` で変更前を実際に読み厳密比較。前からあれば `isNewRegression=false`。さらに**変更前が正しかったか**まで判定する（下記） |
  | **reachability** | 所見が仮定する入力・状態・操作が実在するか。型・上流フィルタ・DBスキーマまで辿り、到達不能なら REFUTED。到達できる場合は **経路が何本あるか・その操作は自然か**まで書かせる（1経路でも通れば UPHELD、では実害を見誤る） |
  | **impact** | 画面表示・保存値・API送信値まで辿る。加えて **提案された修正案自体の副作用**を検証 |

  → `UPHELD` / `DOWNGRADED` / `REFUTED` を **3票の多数決**で確定。割れたら SPLIT のまま人に見せる

- **票数から確信度への変換を機械的に行う**。④の `UPHELD` と⑤の `CONFIRMED` は別語彙で、
  繋ぎ方を決めておかないと「PLAUSIBLE とラベルしたまま High に置く」矛盾が出る

  | 3レンズの票 | 確信度 | ⑤で置ける上限 |
  |---|---|---|
  | UPHELD 3票 | **CONFIRMED** | High |
  | UPHELD 2票（残りが DOWNGRADED） | **PLAUSIBLE** | Medium |
  | UPHELD 2票 + REFUTED 1票 | **SPLIT** | Medium（反対票の根拠を必ず1行添える） |
  | UPHELD 1票以下 | REFUTED / DOWNGRADED | Low 以下または「直さない」 |

  **UPHELD 3票でも、レンズが「コードを読めば確認できる」範囲を超えた根拠（外部ドキュメント・実行環境の振る舞い）に
  依存しているなら CONFIRMED にしない**。3票が同じ誤った前提を共有していただけ、という事故が実測で起きている

- **レンズが留保を書いた票は UPHELD として数えない。**
  「〜は本リポジトリからは検証不能」「バックエンド側は確認できていない」のような但し書きが付いた `UPHELD` は
  **未検証**として扱い、その前提が埋まるまで票に加えない。埋め方は2つ:
  **main が該当リポジトリを自分で読む**か、そのレンズに追加質問を投げて埋めさせる。
  実測では、reachability レンズが「バックエンドが `is_main:0` だけの visit_groups を永続化するかは
  本リポジトリからは検証不能」と**正しく留保したのに**、main がそれを UPHELD 票として数え、
  フロントの送信経路だけで CONFIRMED にして High に置いた（バックエンドを読めば5分で埋まる前提だった）

- **High 候補（CONFIRMED かつ実害あり）には、4枚目の反証レンズ（red）を追加で走らせる。**
  3レンズは「所見が正しいか」を別の観点から見るだけなので、全員が同じ前提を共有していると誤りが揃って通過する。
  red レンズには**所見が誤りである根拠だけを探させる**（支持する材料は集めさせない）:
  - 「この所見が誤りだとしたら、その根拠は何か」だけを調べさせる
  - 根拠が外部ドキュメントなら、**その頁の適用範囲**（製品・バージョン・条件節）を読ませる
  - 「この所見が本当なら、既存の運用ですでに壊れているはずでは？」を確認させる。
    すでに本番で回っている経路なら、所見の前提が間違っている可能性が高い
  - red が誤りの根拠を一つでも挙げたら、**CONFIRMED を取り消して PLAUSIBLE（Medium）に落とす**。
    High に戻すには、その根拠を潰した証拠を示す
  - High 候補が無ければ起動しない。コストは High 候補の件数分だけ

- **legacy レンズは省略不可**。所見の最大の誤りは「既存負債を新規退行と誤認すること」で、実測では10件中6件がこれで潰れた
- **legacy レンズは「変わったか」で止めず、「変更前が正しかったか」まで判定させる。**
  `isNewRegression=true` は「この PR が持ち込んだ」を意味するだけで、「悪くなった」を意味しない。
  変更前が間違っていれば、その所見は**退行ではなく既存不整合の是正**であり、優先度はまるで変わる。
  値・閾値・条件式が変わった所見では、次の3つを必ずやらせる:
  - `git log -S '<変更前の式>'` / `git blame` で、その値が**いつ・どのコミットで・何の名目で**入ったかを追う
  - 同種の処理をリポジトリ全体から grep し、変更前の値が**多数派か外れ値か**を数で示す
  - 外れ値なら「退行」ではなく「既存不整合の部分是正」として報告し、**残っている他の箇所の件数**も添える

  実測では、サブ担当枠の閾値が `< 5` → `< 4` に変わったのを「後方互換の縮小」として Medium で報告したが、
  聞かれてから調べると `< 5` は2021年に3ファイル同時追加された取り違えで、当時から helper は `< 4`、
  現在も**同一ファイル内に `< 5` と `< 4` が併存**していた。5秒の grep で出る事実を3レンズとも見ていない
- **「古い値が残る」「更新されない」系の主張は、その値を上書きしうる全経路を列挙させる。**
  「この変数は経路 X でしか更新されない」→「だから古い値が残る」は、**1つでも上書き経路があれば成立しない**。
  Vue の emit / watcher が絡む場合は、setter・emit・watcher キューの実行順序を実コードで1ステップずつ追わせる。
  実測では、impact レンズが「`previousVisitGroups` は子の emit 経由でしか更新されない」で止めて
  「2つ前の選択が復活する」と結論したが、子の setter が `officeId` の emit **より先**に
  `update:visit-groups` を発火するため毎回上書きされており、主張は成立しなかった
- **sweep（見落とし探索）を並走**させ、**その新規所見も同じ3レンズに2巡目でかける**。ここを飛ばすと1巡目と同じ過剰検出を繰り返す（実測: sweep の新規7件中、実害が残ったのは1件、1件は到達不能で REFUTED）
- **sweep の所見を検証に渡すときは要約せず原文のまま渡す。** 検証パネルは渡された主張しか検証しない。
  1件の所見に複数の論点（例: 「import の方向」と「配置規約そのもの」）が含まれているとき、
  要約で片方に絞ると、落とした論点は検証すらされず報告から消える。
  実測では、この圧縮で明文規約違反を1件取りこぼした。**論点が2つあるなら所見も2件に分けて渡す**
- 「規約違反」の主張は、規約ファイルを実際に読ませて**該当条文を引用させる**。明文が無ければ設計上の好みに格下げ。
  ただし**「明文が無い」の判定は、主張されている論点そのものについて行う**。
  別の論点に明文が無いことを根拠に、明文のある論点まで一緒に格下げしない
- リポジトリ横断の主張（フロントの送信値をバックエンドがどう解釈するか等）は**両方のリポジトリを読ませて**裏取りさせる。
  レンズは自分の作業ディレクトリの外を見に行かないことが多いので、**対象リポジトリの絶対パスをプロンプトに明記する**
- **「この操作はできる／できない」を主張する所見は、それを決めている prop・フラグ・設定の default 値を必ず読ませる。**
  実測では、`require-main-staff="false"` を渡している1画面だけを見て「主担当なしで保存できる」と結論し、
  **その prop の default が `true` で他の4画面はすべて塞がれている**という肝心の事実が報告から落ちた。
  結果、実質到達不能な状態を前提にした所見が High になった。
  「例外を渡している箇所」を見つけたら、**必ず default 側と、渡していない呼び出し元の数**をセットで報告させる
- **外部ドキュメントを根拠にする所見は、「そのドキュメントが対象の実行環境に適用されるか」まで確認させる。**
  コードを読んでも確認できない主張（クラウドの取り込み仕様・ミドルウェアの内部挙動・ライブラリのバージョン差など）は、
  他の所見と同じ扱いで通してはいけない。**主張を支持する一文を1つ見つけた時点で止めない。**
  - ❌ 「公式ドキュメントにこう書いてある」→ 採用
  - ✅ 「その頁はどの製品／どのエージェント／どのバージョン向けか」「対象環境が明記されているか」「条件節（〜が無効な場合、等）が付いていないか」まで読む
  - 適用範囲が確認できなければ **Medium 以下**に置き、「何を測れば確定するか」を1行添える
  - 実測では、レガシーな logging エージェント向けの一文をマネージド環境にそのまま当てはめ、**存在しない問題を High として報告した**
- 「テストが実装を守っていない」という所見は、**テストコードとフィクスチャを読んで**判定させる。「この負のフィクスチャは条件Aと条件Bを同時に変えているので、Aだけを壊しても検出できない」といった形で、コードから機械的に示せるものだけ残す（**テストは実行しない**。実装を書き換えるミューテーション検証も行わない）

### ⑤へ進む前に「全エージェント回収」と「全所見の検証完了」の両方を満たす

⑤に進める条件は2つある。**片方だけでは足りない。**

**条件1: ③④で起動したエージェントが1体でも未回収なら、⑤を書き始めない。**
ここを守らないと、報告を出したあとに所見がトリクル到着し、「訂正1」「訂正2」…と小出しの追記が続いて
読み手が全体像を掴めなくなる。実測では、この状態で報告してしまい**訂正を7回**出す羽目になった。
しかも最後に届いた sweep に、その回で最もユーザーに見える所見（ネイティブのバッジ数が変わる）が入っていた。

- 回収は**催促ループ**で行う。`Bash(sleep, run_in_background)` で待ち、未回収の相手に `SendMessage` で
  「今すぐ `SendMessage({to: "main", ...})` を1回呼べ。未完了なら現時点の分だけでよい」と送る。応答が無ければ繰り返す
- **どうしても返さないエージェントが残ったら、そのレンズ／観点を自分で実行してから⑤を書く。**
  未実施のまま報告しない。特に **sweep を欠いたまま「所見は出揃った」と書かない**

**条件2: sweep の新規所見を含む全所見が3レンズを通過していなければ、⑤を書き始めない。**
sweep は最後に返ってくるため、**「回収が完了して⑤を書いてよくなった瞬間」に未検証の所見が手元に増える**という
構造になっている。条件1を満たした安心感でそのまま報告に流し込むのが典型的な事故。
実測では、この経路で**未検証の sweep 所見がその回の唯一の High になり、あとで誤りと判明して取り下げた**。

- 回収が済んだら、**⑤を書く前に必ず所見の棚卸しをする**。1件ずつ「3レンズ通過済みか」を確認し、未通過があれば2巡目を回す
- **棚卸しは「3レンズ通過済みか」だけでは足りない。Medium 以上に置く所見は1件ずつ「前提が埋まっているか」も確認する。**
  レンズは渡された主張を検証するだけで、その主張が**乗っている前提**は問わないことがある。
  ⑤を書く前に、Medium 以上の各所見について次を自問し、埋まっていなければ**自分で埋めてから**優先度を決める:
  - この所見が成立する前提は何か。その前提を**誰がどう確認したか**を1行で言えるか
  - レンズの回答に「〜は検証不能」「〜は確認できていない」という但し書きが付いていないか
  - 「この操作ができる／できない」を含むなら、それを決めている **default 値**を読んだか
  - 「変更前と変わった」を含むなら、**変更前が正しかったか**を確認したか

  実測では、ここを飛ばしたために「主担当なしのデータが実在する」「変更前の閾値が正しい」という
  未確認の前提に乗った所見を High / Medium で報告し、**ユーザーの一言で2件続けて格下げになった**。
  どちらも grep 1回とバックエンド5分で埋まる前提で、報告前に自分で気付けたもの
- 「自分でコードを読んで確認した」は legacy / reachability / impact のどれか1枚を代替したにすぎない。**3枚揃って初めて検証済み**
- 検証メタに以下の形で明示的に書く（数が合わなければ⑤を出してはいけない）:
  `所見 N件（1巡目 M件 + sweep K件）→ 全 N件が3レンズ通過済み / High 候補 H件は red レンズ通過済み / 自分で代替実施 X件`

## ⑤ 統合報告

**読み手が最初の数行で「何を直すべきか」を掴めることが最優先。** 検証の途中経過を本文に並べない。

**報告は最後に1回、全部入りで出す。** 途中経過・レンズ別の判定・個別の訂正を分割して投げない。
遅れて所見が届いたら、**報告済みの本文を差分で直すのではなく、番号を振り直した完全版を1メッセージで出し直す**
（読み手は「#3 と #7 を直して」と番号で指示する。番号が前のメッセージに散っていると参照できない）。

報告は下記フォーマットに従う。要点は5つ:

1. **優先度で分類する**（High / Medium / Low / 直さない）。実害順に並べるだけでは、読み手が「今どこまで対応すべきか」の線を引けない
2. **全項目に通し番号 `#N` を振る**（High から「直さない」まで通し）。ユーザーが「#2 と #4 を直して」と番号で指示できるようにするため。**セクションごとに 1 から振り直さない**
3. **各項目を「性質 / 新規・既存 / ユーザー影響 / 対策」の4点セットで書く**。所見の文章をそのまま貼らない。「性質」でこれが何の問題か（バグ/規約違反/設計/リリース手順/仕様不一致…）を分類し、「ユーザー影響」は必ず**ユーザーから見て何が起きるか**で書く（「型が嘘」ではなく「保存されていないのに成功トーストが出る」）
4. **「新規/既存」は legacy レンズの結論をそのまま1行にする**（この PR で入ったのか、前からあったのか）。
   読み手が最初に知りたいのは「自分がこの PR で壊したのか」で、対応の要否がここで決まる。
   **「直さない」の既存負債だけでなく全項目に付ける**。既存と判定したなら**同型の既存実装を1つ示す**
5. **性質がバグ（潜在バグ含む）の項目には「原因」を1行足して5点セットにする**（性質 / 新規・既存 / **原因** / ユーザー影響 / 対策）。
   原因は**なぜそうなるかの機構**を、症状の言い換えにならないように書く（「タイトルが誤る」ではなく
   「Helmet が全インスタンスを再集計し、最後にマウントされた画面の title を採用するため」）。
   これが無いと読み手が対策の妥当性を判断できず、誤った直し方を選ぶ。バグ以外（規約違反・設計・確認事項）には付けない

```
## PR #<番号> レビュー結果（検証済み・修正なし）

**結論**: <1〜2行。実害のあるバグは何件か。High が何件、この PR で直したいものが何件か>

---

### 🔴 High — マージ/リリース前に必ず

**#1　<一行で問題を言い切る>**　`<file:line>` or `<関連PR等>`
- **性質**: <バグ / リリース手順 / 規約違反 / 仕様不一致 / 設計 / …>
- **新規/既存**: <この PR で入った（新規退行） / 前からある既存負債（同型の既存実装を1つ挙げる）>
- **原因**: <バグのときのみ。なぜそうなるかの機構を1行。症状の言い換えにしない>
- **ユーザー影響**: <ユーザーの操作 → 実際に起きること。「なし」なら「なし」と書く>
- **対策**: <具体的にどう直すか。有害な修正案があれば ⚠️ で警告を添える>

### 🟡 Medium — この PR で直したい
（同じ形式で #2, #3, …）

### 🟢 Low — 気が向いたら
（同じ形式）

### ⚪ 直さない（判断の記録）
（同じ形式。ただし3点目は「対策」でなく **判断**: なぜ直さないかの根拠）

**#N　その他の些末な指摘（M件）**
- **性質**: 表記・好みの範囲
- **内訳**: <1行に列挙>
- **判断**: 実害なし。記録として残すが対応不要

---

### 📋 検証メタ

- 所見 N件 → 取り下げ（REFUTED）X件 / 重大度を下げた（DOWNGRADED）Y件（一覧は聞かれたら出す）
- **検証カバレッジを数で書く**: `所見 N件（1巡目 M件 + sweep K件）→ 全 N件が3レンズ通過済み / High 候補 H件は red レンズ通過済み / 自分で代替実施 X件`。
  **数が合わない状態で⑤を出さない**（合わないなら2巡目を回してから書く）
- **PLAUSIBLE のまま残した所見があれば、件数と「何を測れば確定するか」を1行で書く**
- 誤りの傾向を1行で正直に書く（例: 「既存パターンを新規退行と誤認したのが最多」）
- 検証中に棄却した捏造所見があれば明記する（どのエージェントが何件、どう確認して棄却したか）
- **未回収のエージェントがあれば明記する**（誰の分を自分で代替実施したか。全員回収できたなら「全員回収」と書く）
- フロー逸脱があれば1行（例: 規約担当が独断で lint を実行した）
- worktree: <パス>。手動作成のため自動削除されない。**「レビュー完了」と言ってもらえれば⑥で削除する**と添える
```

### 優先度の付け方

| | 基準 |
|---|---|
| 🔴 **High** | マージ/リリースすると実際に壊れる。コード修正が要らない手順の問題もここ（ただし下記「所見にしないもの」を除く）。**CONFIRMED（3レンズ全票 UPHELD）かつ red レンズを通過したものだけ** |
| 🟡 **Medium** | 今は壊れていないが、この PR の責任範囲で直すべき。潜在バグ・明文規約違反・仕様との不一致 |
| 🟢 **Low** | 直さなくても回る。保守性・a11y・ドキュメントの誤り・DS 側に起因する回避策 |
| ⚪ **直さない** | 既存負債 / 別リポジトリ起因 / 申告済みのスコープ外変更 / 些末。**判断の根拠を必ず書く** |

- **確信度は優先度の上限を決める。🔴 High に置けるのは CONFIRMED だけ。PLAUSIBLE は Medium 止まり**とし、
  「**何を測れば CONFIRMED になるか**」を1行添える（例: 「stg にデプロイして LogEntry の payload 種別を1回見れば確定する」）。
  ここを分離しておかないと、「PLAUSIBLE」と正しくラベルしたまま High に置くという矛盾した報告が出る。
  読み手は優先度だけを見て動くので、**ラベルで注記しても効かない**。実測でこれをやり、唯一の High が誤りだった
- **「直さない」を削らない。** 見なかったのか、見て判断したのかを読み手が区別できる必要がある。ただし些末なものは1項目にまとめて内訳を1行で済ませる
- 既存負債は「直さない」に置く。**なぜ既存と判定したか**（どのファイルに同型の既存実装があるか）は各項目の「新規/既存」欄に書く。これが無いと legacy レンズの結論が読み手に伝わらない

### 所見にしないもの（優先度を付けずに落とす）

- **フロント/バックエンドのリリース順序。** 対となるバックエンド PR が未マージ・未デプロイであることを理由に
  「フロント先行リリースで保存が効かない / 設定が戻る」を所見に挙げない。**CrossLog では対の PR を必ず同時にリリースする**運用が
  確立しており、毎回同じ指摘になるだけでノイズになる。
  - バックエンド PR の**存在と対応関係の確認**は続けてよい（フロントが送るフィールド名が back の strong parameters と
    一致しているか等、**内容の突合**は有効な所見になる）。落とすのは「先に出したら壊れる」という**順序そのものの指摘**
  - PR 本文が参照する番号が Issue 番号で実 PR 番号と違う、といった軽微な記載ミスも所見にしない（聞かれたら答える程度）

## ⑥ 後片付け（worktree の削除）

**ユーザーが「レビュー完了」「もう確認した」「片付けて」等の完了指示を出したら、②で作った worktree を削除する。**

- **⑤の報告直後に勝手に消さない。** ユーザーは報告を読んだあとその worktree で実際に画面を触って確認する。完了指示を待つ
- 手順:

```bash
git -C <worktree パス> status --short          # 1. clean か確認
# 2. その worktree の中にいるなら ExitWorktree(action: "keep") で元ディレクトリへ戻る
git -C <repo> worktree remove <worktree パス>  # 3. 削除
git -C <repo> worktree list                    # 4. 消えたことを確認
```

- **`git status` が dirty なら消さない。** 差分の中身を見せて、消していいかユーザーに確認する。ユーザーが手元で試した変更が残っている可能性がある
- **`--force` は使わない。** remove が失敗したら理由をそのまま見せて判断を仰ぐ
- **`worktree remove` はブランチを消さない。** ②で `-b` を付けて作ったローカルブランチが残る。消すかどうかは**必ず確認してから**（`git branch -d '<branch>'`）。同名ブランチでこれから作業する予定があるかもしれない

## 注意

- **判断はすべて読み取りで行う。** コードを修正しない。lint / test / ビルド（＝所見を出すための実行）は一切しない。判断に使うのは Read / Grep / `git`（`show` / `diff` / `log`）/ `gh` だけ
  - **例外は②の依存インストールだけ**（`mise trust` と `yarn install` 等）。これはレビューのための実行ではなく、レビュー後にユーザーがその worktree で画面を触るための環境準備なので必ず実行する。読み取り専用を理由に飛ばさない
- 終了時に `git status` が clean であることを確認する（worktree の追加以外に何も変えていないこと）
- **取り下げた所見を本文に列挙しない**。件数だけ添える。実害があるものが埋もれる
- **報告を小出しにしない。** 全エージェントの回収前に⑤を書き始めると、以降ずっと訂正の追記になる。
  すでに出してしまったら、追記を重ねず**完全版を1メッセージで出し直す**
- **PR 本文の「動作確認手順」を読んでから優先度を付ける。** そこに書かれている挙動は「申告済みの意図」であって
  バグではない。実測では、本文の確認手順を読み落として意図した挙動を Medium のバグと誤判定した
- **確信度・新規/既存・重大度を多列テーブルに詰め込まない**。⑤の「優先度セクション + 通し番号 + 3点セット」の箇条書きが一番読める
- **1項目に根拠の引用や条文を詰め込まない。** 「性質 / 新規・既存 / ユーザー影響 / 対策」の4行（バグなら「原因」を足して5行）に収め、条文やコード引用は最小限で添える。詳細は聞かれてから出す
- **自分の判断で REFUTED を握り潰さない**。迷うものは残して人に見せる
- 過剰検出があったら件数で正直に書く。ただし短く（自己批判で直すべきものを埋もれさせない）
- `qa-review-loop` が無いリポジトリでは、④のルールをそのまま自分で実行する（Workflow なら所見×3レンズを `pipeline` + `parallel`、無ければ Agent を3並列）
- ④は所見数 × 3 + High 候補数（red レンズ）+ sweep 分のエージェントを起動する。規模が大きいので、ユーザーが多エージェント実行に opt-in していない場合は先に確認する
