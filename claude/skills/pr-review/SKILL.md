description: PR の URL / 番号を渡されたら、worktree でそのブランチに切り替え → code-review で所見を出す → qa-review-loop の検証専用モードで所見を敵対的に裏取り → 統合報告、までを一気通貫で行う。「このPRレビューして」「PR見て」「レビューして裏取りまでして」等、PR の URL や番号とともにレビューを頼まれたら使う。コード修正は一切行わない読み取り専用のフロー。
---

PR を渡されたら、**隔離された worktree でレビューし、所見を敵対的に検証してから報告する**までを1本で回す。
**コードは一切修正しない。** 修正を求められたらこのスキルの範囲外で、検証結果を渡したうえで別途指示を取る。

## 全体の流れ

```
PR URL → ① PR情報取得 → ② worktree 切り替え → ③ /code-review → ④ qa-review-loop(検証専用) → ⑤ 統合報告
```

各段は前段の出力を入力にする。**②を飛ばして main checkout でレビューしない**（作業中のツリーを汚す・別ブランチを読んでしまう）。

---

## ① PR 情報を取得し「変更の意図」を確定する

```bash
gh pr view <番号> --repo <owner/repo> --json number,title,body,headRefName,baseRefName,state,additions,deletions,changedFiles
```

- `body` から **変更の意図** を抽出する。後段の検証エージェントはこれが無いと**意図的な変更をバグとして誤検出する**
- 同時に **「チームが意図的に選んだ設計判断」**（PR本文が「これは仕様」と書いている点）を切り出しておく。これも後段に必須
- `baseRefName` を控える。**変更前コードとの比較基準**として④で使う最重要の入力

## ② worktree に切り替える

`worktree` スキルがあればその方針に従う。無い場合の最小手順:

```bash
git -C <repo> fetch origin '<headRefName>'
git -C <repo> worktree add .claude/worktrees/<slug> -b '<headRefName>' 'origin/<headRefName>'
```
→ `EnterWorktree` に **`path` を渡して**進入する。

- **`EnterWorktree` の `name` は使わない**。新規ブランチを切ってしまい、既存のリモートブランチをチェックアウトできない
- 既に同ブランチの worktree があれば（`git worktree list`）作らず再利用する。同一ブランチは2つの worktree に同時チェックアウトできない
- **進入直後に `mise trust` を実行する**（mise 管理のリポジトリ = crosslog-front / webapp）。`worktree` スキルの必須セットアップで、読み取り専用フローでも省略しない。実測では、これを飛ばしたまま進んで後続の `git` / `gh` 実行時に `mise ERROR ... not trusted` を踏んだ
- **依存インストール（`yarn install` 等）は `run_in_background` で走らせる。** レビュー自体は Read / Grep / `git` / `gh` しか使わないので待つ必要はないが、**レビュー結果を受けてユーザーがその worktree で実際に画面を触って確認する**ため、環境は整えておく。バックグラウンドなので③④の待ち時間には乗らない
  - 完了を待たずに③へ進む。レビュー中に lint / test / dev サーバーを起動することは無いので、インストールの成否がレビューをブロックすることもない
- `.worktreeinclude` は手動 `git worktree add` では処理されない。読み取り専用フローでは `.env` 等が無くても支障ないので、コピーし直さない
- 進入以降、**Read / Grep のパスはすべて worktree 配下に切り替える**。進入前の会話に残っている main checkout の絶対パスを使い続けると別ツリーを読む
- 手動 `git worktree add` した worktree は**セッション終了時に自動削除されない**。⑤の報告で掃除方法を伝える

## ③ /code-review で所見を出す

`Skill` で `code-review` を PR URL 付きで起動する。出力は `file` / `line` / `summary` / `failure_scenario` の JSON 配列。

- **`code-review` は `disable-model-invocation` のため `Skill` ツールからは起動できない**（`Skill code-review cannot be used with Skill tool` が返る）。ユーザーが `/code-review` と打った時しか動かないので、このフローでは**最初から自前でレビューパネルを組む**
  - 変更ファイルを観点別に分割し、**独立した Agent を並列起動**する（例: 正しさ / 規約・配置 / テスト網羅 / 周辺への影響）。各エージェントには PR の変更意図と `baseRefName` を渡し、`file` / `line` / `summary` / `failure_scenario` の JSON で返させる
  - 同名の `review` スキルは GitHub PR 向けだが**散文レビューを返す**ので、④に渡す構造化所見としては使いにくい。使うなら出力形式を明示して上書きする

- ここでは**所見を絞り込まない**。recall 重視で出させ、取捨は④に委ねる
- **lint / test は実行しない。** 判断はすべてコードを読んで行う

### 規約チェックで必ず踏むこと（ここが一番漏れる）

- **CLAUDE.md が名指しで参照しているドキュメントを必ず辿って読む。** 自動注入される `.claude/rules/*.md` だけで済ませない。
  CLAUDE.md に「ファイル配置は `docs/policies/directory-structure.md` を必ず読むこと」のような指示があれば、その実ファイルを開く。
  実測では、これを飛ばしたせいで「feature 内に `utils/` を作らない」という明文規約への違反を1巡目で見落とした
- **lint の baseline / suppression ファイルを開く**（`eslint-suppressions.json` 等）。
  変更ファイルがそこに登録されていないか確認する。**登録済みのファイルに新規コードを足すと、規約違反が恒久的に不可視になる**。
  実測では `unicorn/filename-case` が baseline で握り潰されており、`yarn lint` は緑のまま通っていた
- **リネーム・移動・新規ファイルが差分にあれば、配置規約とファイル名規約を必ず1件ずつ照合する**

## ④ qa-review-loop を検証専用モードで回す

`Skill` で `qa-review-loop` を起動し、**修正なしの検証専用モード**であることを明示する。渡す入力:

1. ③の所見リスト（`file:line` / 主張 / 失敗シナリオ / 提案された修正）
2. ①の変更の意図
3. ①の「チームが意図的に選んだ設計判断」
4. ②の比較基準（`baseRefName`）

### qa-review-loop に上乗せする必須ルール

素の qa-review-loop はこれらを必須にしていない。**毎回明示的に指示する。**

- **所見1件につき3レンズを並列**（1エージェントに束ねない。束ねると結論が相互汚染する）

  | レンズ | 役割 |
  |---|---|
  | **legacy** | `git show <base>:<path>` で変更前を実際に読み厳密比較。前からあれば `isNewRegression=false` |
  | **reachability** | 所見が仮定する入力・状態・操作が実在するか。型・上流フィルタ・DBスキーマまで辿り、到達不能なら REFUTED |
  | **impact** | 画面表示・保存値・API送信値まで辿る。加えて **提案された修正案自体の副作用**を検証 |

  → `UPHELD` / `DOWNGRADED` / `REFUTED` を **3票の多数決**で確定。割れたら SPLIT のまま人に見せる

- **legacy レンズは省略不可**。所見の最大の誤りは「既存負債を新規退行と誤認すること」で、実測では10件中6件がこれで潰れた
- **sweep（見落とし探索）を並走**させ、**その新規所見も同じ3レンズに2巡目でかける**。ここを飛ばすと1巡目と同じ過剰検出を繰り返す（実測: sweep の新規7件中、実害が残ったのは1件、1件は到達不能で REFUTED）
- **sweep の所見を検証に渡すときは要約せず原文のまま渡す。** 検証パネルは渡された主張しか検証しない。
  1件の所見に複数の論点（例: 「import の方向」と「配置規約そのもの」）が含まれているとき、
  要約で片方に絞ると、落とした論点は検証すらされず報告から消える。
  実測では、この圧縮で明文規約違反を1件取りこぼした。**論点が2つあるなら所見も2件に分けて渡す**
- 「規約違反」の主張は、規約ファイルを実際に読ませて**該当条文を引用させる**。明文が無ければ設計上の好みに格下げ。
  ただし**「明文が無い」の判定は、主張されている論点そのものについて行う**。
  別の論点に明文が無いことを根拠に、明文のある論点まで一緒に格下げしない
- リポジトリ横断の主張（フロントの送信値をバックエンドがどう解釈するか等）は**両方のリポジトリを読ませて**裏取りさせる
- 「テストが実装を守っていない」という所見は、**テストコードとフィクスチャを読んで**判定させる。「この負のフィクスチャは条件Aと条件Bを同時に変えているので、Aだけを壊しても検出できない」といった形で、コードから機械的に示せるものだけ残す（**テストは実行しない**。実装を書き換えるミューテーション検証も行わない）

## ⑤ 統合報告

**読み手が最初の数行で「何を直すべきか」を掴めることが最優先。** 取り下げた所見・検証の途中経過を本文に並べない。

```
## PR #<番号> レビュー結果（検証済み・修正なし）

**結論**: <1〜2行。所見 N 件のうち実害が残ったのは何件か>

### 今対応すべき（実害があるものだけ・重大度順）
1. <file:line> — <何がどう壊れるか>。修正方針: <一言。有害な修正案があれば警告を添える>
（無ければ「なし」と明記）

### 直さない（既存負債 / 別issue / スコープ外）
- <file:line> — <1行・理由>

### 補足
- 取り下げ（REFUTED）: N件 / 重大度を下げたもの: M件（一覧は聞かれたら出す）
- 誤りの傾向を1行で正直に書く（例: 「変更前と比較しなかったのが原因で6件潰れた」）
- worktree: <パス>。手動作成のため自動削除されない。不要なら `git worktree remove <パス>`
```

## 注意

- **判断はすべて読み取りで行う。** コードを修正しない。lint / test / ビルド（＝所見を出すための実行）は一切しない。判断に使うのは Read / Grep / `git`（`show` / `diff` / `log`）/ `gh` だけ
  - **例外は②の依存インストールだけ**（`mise trust` と `yarn install` 等）。これはレビューのための実行ではなく、レビュー後にユーザーがその worktree で画面を触るための環境準備なので必ず実行する。読み取り専用を理由に飛ばさない
- 終了時に `git status` が clean であることを確認する（worktree の追加以外に何も変えていないこと）
- **取り下げた所見を本文に列挙しない**。件数だけ添える。実害があるものが埋もれる
- **確信度・新規/既存・重大度を多列テーブルに詰め込まない**。実害順の箇条書きが一番読める
- **自分の判断で REFUTED を握り潰さない**。迷うものは残して人に見せる
- 過剰検出があったら件数で正直に書く。ただし短く（自己批判で直すべきものを埋もれさせない）
- `qa-review-loop` が無いリポジトリでは、④のルールをそのまま自分で実行する（Workflow なら所見×3レンズを `pipeline` + `parallel`、無ければ Agent を3並列）
- ④は所見数 × 3 + sweep 分のエージェントを起動する。規模が大きいので、ユーザーが多エージェント実行に opt-in していない場合は先に確認する
