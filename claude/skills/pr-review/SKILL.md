name: pr-review
description: PR の URL / 番号を渡されたら、worktree でそのブランチに切り替え → 観点別レビュアーで所見を出す → 複数レンズで所見を敵対的に検証する → 実害のあるものだけを統合報告、までを一気通貫で行う。「このPRレビューして」「PR見て」「レビューして裏取りまでして」等、PR の URL や番号とともにレビューを頼まれたら使う。コード修正は一切行わない読み取り専用のフロー。
---

PR を渡されたら、**隔離された worktree でレビューし、所見を敵対的に検証してから報告する**までを1本で回す。
**コードは一切修正しない。** 修正を求められたらこのスキルの範囲外で、検証結果を渡したうえで別途指示を取る。

**探しているのは実害があるものだけ。** 「ユーザーから見て何が起きるか」を書けない所見は、
正しくても報告しない（→「所見にしないもの」）。検証のコストも報告の行数も、実害のある所見に寄せる。

## 全体の流れ

```
PR URL → ① PR情報取得 → ② 規模見積もりと実行確認 → ③ worktree 切り替え
       → ④ レビュー＆検証（Workflow 1本） → ⑤ 棚卸し → ⑥ 統合報告
       → ⑦ 後片付け（ユーザーが「レビュー完了」と言ったら）
```

- **③を飛ばして main checkout でレビューしない**（作業中のツリーを汚す・別ブランチを読んでしまう）
- **④は所見の生成と検証を1つの Workflow で回す。** 途中で main に戻さない。`agent()` の戻り値が結果なので、取りこぼしは起きない
- **⑥は⑤の棚卸しが済んでから1回だけ出す。** 途中経過・レンズ別の判定・個別の訂正を分割して投げない
- ⑥で終わりではない。**⑦はユーザーの完了指示を待って実行する**（報告直後に勝手に消さない。ユーザーがその worktree で画面を触って確認する時間が要る）

このスキルは `code-review` / `qa-review-loop` に委譲しない。**所見の生成も検証も自前で組む**
（`code-review` は `disable-model-invocation` のため `Skill` ツールから起動できず、ユーザーが `/code-review` と
打った時しか動かない。`qa-review-loop` は④の必須ルールを持たないので、結局すべて上書き指示することになる）。

## 参照ファイル

**①の直後に `references.local/` の有無を確認する**（`ls` 1回）。git 管理外の領域で、
このスキル本文には書けない情報を置いてある。**無ければ本文のルールだけで進めてよい。**

| ファイル | 中身 | いつ読むか |
|---|---|---|
| `references.local/<組織名>.md` | リポジトリ固有のセットアップ手順・所見にしない運用ルール | 対象がそのリポジトリ群のとき、**③の前に** |
| `references.local/postmortems.md` | 本文の各ルールが生まれた失敗の記録（`P1`〜`P14`） | ルールの意図が掴めないとき・ルールを外したくなったとき |

本文中の `→ P<n>` は `postmortems.md` の該当項目を指す。**根拠が要るときだけ開けばよく、通読は不要。**

## ① PR 情報を取得し「変更の意図」を確定する

```bash
gh pr view <番号> --repo <owner/repo> --json number,title,body,headRefName,baseRefName,state,additions,deletions,changedFiles
```

- `body` から **変更の意図** を抽出する。後段の検証レンズはこれが無いと**意図的な変更をバグとして誤検出する**
- 同時に **「チームが意図的に選んだ設計判断」**（PR本文が「これは仕様」と書いている点）を切り出しておく。これも後段に必須
- `baseRefName` を控える。**変更前コードとの比較基準**として④で使う最重要の入力
- **PR 本文の「動作確認手順」を読む。** そこに書かれている挙動は「申告済みの意図」であってバグではない（→ P1）

## ② 規模を見積もってユーザーに確認する

④は多数のサブエージェントを起動する。**着手前に規模を出して確認を取る**（終わってからコストを告げない）。

```
変更 <N> ファイル / +<A> -<D> 行
→ 観点別レビュアー 4体 + sweep 1体 = 5体で所見を出し、
   実害のあるものだけに legacy 1体、生き残りに reachability / impact 2体、
   High 候補には red 1体を追加します
   （所見20件のうち実害ありが10件程度なら、合計 25〜35 体）。
   このまま進めますか？
```

- セッションに Workflow の規模ガイドライン（既定は「10体未満」）が出ていて、見積もりがそれを超えるなら**必ず確認する**
- 「重くていいから全部見て」と言われたら、④の省略（後述の「既存確定で2レンズを省く」）を無効化して全件3レンズにする
- 規模を下げたいと言われたら、観点別レビュアーを減らすのではなく**④の省略を効かせる**。
  所見の入口を狭めると見落としが増え、このフローの価値が消える

## ③ worktree に切り替える

**リポジトリ固有のセットアップ手順が `references.local/` にあれば、先にそれを読む。**
（依存インストール・環境変数ファイルのコピー・ツールチェーンの信頼設定など、ここに書けないものが入っている）

worktree の運用スキルがあればその方針に従う（`references.local/` が該当スキル名を指定していればそれを使う）。
無い場合の最小手順:

```bash
git -C <repo> fetch origin '<headRefName>'
git -C <repo> worktree add .claude/worktrees/<slug> -b '<headRefName>' 'origin/<headRefName>'
```
→ `EnterWorktree` に **`path` を渡して**進入する。

- **`EnterWorktree` の `name` は使わない**。新規ブランチを切ってしまい、既存のリモートブランチをチェックアウトできない
- 既に同ブランチの worktree があれば（`git worktree list`）作らず再利用する。同一ブランチは2つの worktree に同時チェックアウトできない
- **依存インストールは `run_in_background` で走らせ、完了を待たずに④へ進む。**
  レビュー自体は Read / Grep / `git` / `gh` しか使わないので待つ必要はないが、
  **レビュー結果を受けてユーザーがその worktree で実際に画面を触って確認する**ため、環境は整えておく
- **git 管理外の環境ファイル（`.env` 等）を main checkout からコピーする。**
  手動 `git worktree add` では、`EnterWorktree` が worktree を「作る」ときのコピー機構が働かない。
  レビュー自体には不要だが、後から「起動できない」と気付くと確認が止まる
- 進入以降、**Read / Grep のパスはすべて worktree 配下に切り替える**。進入前の会話に残っている main checkout の絶対パスを使い続けると別ツリーを読む
- 手動 `git worktree add` した worktree は**セッション終了時に自動削除されない**。⑥の報告でパスを伝え、ユーザーの完了指示を受けて⑦で削除する

## ④ レビュー＆検証（Workflow 1本）

所見の生成（Find）と検証（Screen / Verify / Challenge）を**1つの Workflow に収める**。

`Workflow` を使うのはこのスキルが指示しているため正当だが、**②の確認を取ってから呼ぶ**。

### なぜ Workflow か（Agent + SendMessage で組まない）

`agent()` の戻り値がそのまま結果になり、`schema` を付ければ構造化 JSON が検証済みで返る。
**サブエージェントに `SendMessage({to:"main"})` で結果を送らせる方式を使ってはいけない。**
回収の失敗は指示の不足ではなく方式の問題で、戻り値で受ければ構造的に起きない（→ P3）。

`Workflow` が使えない環境では `Agent` を並列起動し、**`Agent` の戻り値で回収する**（これも `SendMessage` は使わない）。

### Find — 所見を出す

- 変更ファイルを観点別に分割し、**独立したエージェントを並列起動**する（例: 正しさ / 規約・配置 / テスト網羅 / 周辺への影響）
- **各所見に「ユーザーから見て何が起きるか」を必ず書かせる**（`user_impact`）。
  ここが「なし」「表記の問題」「保守性が下がる」にしかならない所見は**出させない**。
  レビュアーは放っておくと表記・好みの指摘で件数を稼ぐので、プロンプトで明示的に禁じる
- **sweep（見落とし探索）を別枠にせず、同じ Find フェーズに並べる。**
  後段に置くと「他が全部検証し終わった瞬間に未検証の所見が手元に増える」構造になる（→ P2）
- ここでは**所見を絞り込まない**。recall 重視で出させ、取捨は検証段に委ねる
- **lint / test は実行しない。** 判断はすべてコードを読んで行う

### Screen → Verify — 段階化した3レンズ

3レンズ（legacy / reachability / impact）の多数決で `UPHELD` / `DOWNGRADED` / `REFUTED` を確定する。
ただし**全件に3枚を並べない。legacy を先に1枚だけ流す。**

**Screen の前に、実害の無い所見を機械的に落とす。** Find が `user_impact` を書けていない所見、
「所見にしないもの」に該当する所見は、**1枚も回さずに件数だけ持って落とす**。
検証コストは実害のある所見にだけ払う。

| レンズ | 役割 |
|---|---|
| **legacy** | `git show <base>:<path>` で変更前を実際に読み厳密比較。前からあれば `isNewRegression=false`。さらに**変更前が正しかったか**まで判定する（下記） |
| **reachability** | 所見が仮定する入力・状態・操作が実在するか。型・上流フィルタ・DBスキーマまで辿り、到達不能なら REFUTED。到達できる場合は **経路が何本あるか・その操作は自然か**まで書かせる（1経路でも通れば UPHELD、では実害を見誤る） |
| **impact** | 画面表示・保存値・API送信値まで辿る。加えて **提案された修正案自体の副作用**を検証 |

- **legacy が `git show` の実出力で「変更前と同一挙動」を示せた所見は、そこで「既存」として確定し、残り2レンズを省く。**
  一次資料で決着がつくので3枚を待つ必要がない。削減幅が一番大きい段（→ P4）
  - **例外: 主張された実害が High 級なら、既存と判定されても2レンズを回す。** 既存負債でも実害があれば報告の価値が変わる
  - ②で「全部見て」と言われている場合はこの省略を無効化する
- 生き残りは reachability / impact を**並列で2枚**。legacy の票と合わせて3票にする
- **所見1件につき1レンズ1エージェント。1体に束ねない**（束ねると結論が相互汚染する）
- 割れたら SPLIT のまま人に見せる

### Challenge — 反証（red）と復権（green）

3レンズは「所見が正しいか」を別の観点から見るだけなので、**全員が同じ前提を共有していると誤りが揃って通過する**。
方向を明示した4枚目を、対象を絞って追加する。

- **red（反証）: High 候補（UPHELD 3票かつ実害あり）に走らせる。所見が誤りである根拠だけを探させる**（支持する材料は集めさせない）
  - 「この所見が誤りだとしたら、その根拠は何か」だけを調べさせる
  - 根拠が外部ドキュメントなら、**その頁の適用範囲**（製品・バージョン・条件節）を読ませる
  - 「この所見が本当なら、既存の運用ですでに壊れているはずでは？」を確認させる。
    すでに本番で回っている経路なら、所見の前提が間違っている可能性が高い
  - red が誤りの根拠を一つでも挙げたら、**CONFIRMED を取り消して PLAUSIBLE に落とす**。戻すにはその根拠を潰した証拠が要る

- **green（復権）: 実害が High 級だと主張されたのに REFUTED / DOWNGRADED になった所見に走らせる。所見が正しい根拠だけを探させる**
  - red だけだと検証が**格下げ方向にしか働かない**。潰された所見は件数だけになって本文から消える（⑥）ので、
    3レンズが同じ誤った前提を共有して揃って否定しても誰も気付けない
  - green が根拠を挙げたら、**その所見を SPLIT に戻して⑥の「要確認」に載せる**（勝手に復権させず人に見せる）
  - 対象は「実害が大きいと主張された所見が潰された」ケースだけなので、件数は通常わずか

- **レンズには必ず `basis`（何を読んで判断したか）を返させ、REFUTED が揃った所見はその `basis` を突き合わせる。**
  3枚が実質同じ一文・同じファイルにだけ依拠していたら**票の独立性が無い**。⑤でフラグを立てて人に見せる

### 票から確信度への変換

④の `UPHELD` と⑥の `CONFIRMED` は別語彙なので、繋ぎ方を機械的に決めておく。
決めておかないと「PLAUSIBLE とラベルしたまま High に置く」矛盾が出る（→ P5）。

| 3レンズの票 | 確信度 |
|---|---|
| UPHELD 3票（red 通過済み） | **CONFIRMED** |
| UPHELD 3票（red 未通過 / red が反証を挙げた） | **PLAUSIBLE** |
| UPHELD 2票 | **PLAUSIBLE**（REFUTED が混じるなら SPLIT として反対票の根拠を1行添える） |
| UPHELD 1票以下 | REFUTED / DOWNGRADED（green が復権させたら SPLIT） |

- **UPHELD 3票でも、レンズが「コードを読めば確認できる」範囲を超えた根拠（外部ドキュメント・実行環境の振る舞い）に
  依存しているなら CONFIRMED にしない**。3票が同じ誤った前提を共有していただけ、という事故が起きている（→ P5）
- **レンズが留保を書いた票は UPHELD として数えない。**
  「〜は本リポジトリからは検証不能」「バックエンド側は確認できていない」のような但し書きが付いた `UPHELD` は
  **未検証**として扱い、その前提が埋まるまで票に加えない。埋め方は2つ:
  **main が該当リポジトリを自分で読む**か、そのレンズに追加質問を投げて埋めさせる（→ P6）

### 全エージェントのプロンプトに必ず入れる

Find の観点別レビュアーも Screen / Verify / Challenge の各レンズも、下記を**プロンプト本文に明記する**。
スキル本文に書いてあってもサブエージェントには伝わらない。

- **実行禁止の明示**: 「コードは修正しない。`lint` / `test` / ビルドは実行しない。使うのは Read / Grep / `git`（`show`/`diff`/`log`）/ `gh` だけ」（→ P7）
- **ライブラリのソースの探し方**: 「gem・npm パッケージの実装を読むときは `bundle show <gem>` / `gem contents <gem>`（コンテナ内なら `docker compose exec <service> bundle show <gem>`）、
  `node_modules/<pkg>` で場所を特定する。`find /` などファイルシステム全体の走査は禁止」。
  場所が分からないと `find /` に走り、複数レンズが並列で全ディスクを舐めてマシンが固まる
- **リポジトリ固有の「所見にしないもの」**: `references.local/` に運用由来の除外ルールがあれば、
  **その条文をプロンプトに転記する**。書かないと毎回同じ指摘が High で上がってくる
- **①の変更の意図・設計判断・`baseRefName`・worktree の絶対パス**。リポジトリ横断の主張を検証させるときは
  **相手リポジトリの絶対パスも明記する**。レンズは自分の作業ディレクトリの外を見に行かないことが多い

### 規約チェックで必ず踏むこと（ここが一番漏れる）

- **CLAUDE.md が名指しで参照しているドキュメントを必ず辿って読む。** 自動注入される `.claude/rules/*.md` だけで済ませない。
  CLAUDE.md に「ファイル配置は `docs/policies/directory-structure.md` を必ず読むこと」のような指示があれば、その実ファイルを開く（→ P8）
- **lint の baseline / suppression ファイルを開く**（`eslint-suppressions.json` 等）。
  変更ファイルがそこに登録されていないか確認する。**登録済みのファイルに新規コードを足すと、規約違反が恒久的に不可視になる**。
  lint が緑でも規約違反は在りうる（→ P9）
- **リネーム・移動・新規ファイルが差分にあれば、配置規約とファイル名規約を必ず1件ずつ照合する**

### レンズに必ずやらせる裏取り

- **legacy レンズは省略不可**（既存確定で残り2枚を省くことはあっても、legacy 自体は全件に流す）。
  所見の最大の誤りは「既存負債を新規退行と誤認すること」
- **legacy レンズは「変わったか」で止めず、「変更前が正しかったか」まで判定させる。**
  `isNewRegression=true` は「この PR が持ち込んだ」を意味するだけで、「悪くなった」を意味しない。
  変更前が間違っていれば、その所見は**退行ではなく既存不整合の是正**であり、優先度はまるで変わる。
  値・閾値・条件式が変わった所見では、次の3つを必ずやらせる（→ P10）:
  - `git log -S '<変更前の式>'` / `git blame` で、その値が**いつ・どのコミットで・何の名目で**入ったかを追う
  - 同種の処理をリポジトリ全体から grep し、変更前の値が**多数派か外れ値か**を数で示す
  - 外れ値なら「退行」ではなく「既存不整合の部分是正」として報告し、**残っている他の箇所の件数**も添える
- **「古い値が残る」「更新されない」系の主張は、その値を上書きしうる全経路を列挙させる。**
  「この変数は経路 X でしか更新されない」→「だから古い値が残る」は、**1つでも上書き経路があれば成立しない**。
  イベント駆動（emit / watcher / リスナー）が絡む場合は、setter・発火・キューの実行順序を実コードで1ステップずつ追わせる（→ P11）
- **「この操作はできる／できない」を主張する所見は、それを決めている prop・フラグ・設定の default 値を必ず読ませる。**
  「例外を渡している箇所」を見つけたら、**必ず default 側と、渡していない呼び出し元の数**をセットで報告させる（→ P12）
- **外部ドキュメントを根拠にする所見は、「そのドキュメントが対象の実行環境に適用されるか」まで確認させる。**
  **主張を支持する一文を1つ見つけた時点で止めない**（→ P5）
  - ❌ 「公式ドキュメントにこう書いてある」→ 採用
  - ✅ 「その頁はどの製品／どのエージェント／どのバージョン向けか」「対象環境が明記されているか」「条件節（〜が無効な場合、等）が付いていないか」まで読む
  - 適用範囲が確認できなければ **🟠 要確認**に置き、「何を測れば確定するか」を1行添える
- 「規約違反」の主張は、規約ファイルを実際に読ませて**該当条文を引用させる**。明文が無ければ設計上の好みに格下げ。
  ただし**「明文が無い」の判定は、主張されている論点そのものについて行う**。
  別の論点に明文が無いことを根拠に、明文のある論点まで一緒に格下げしない
- 「テストが実装を守っていない」という所見は、**テストコードとフィクスチャを読んで**判定させる。
  「この負のフィクスチャは条件Aと条件Bを同時に変えているので、Aだけを壊しても検出できない」といった形で、
  コードから機械的に示せるものだけ残す（**テストは実行しない**。実装を書き換えるミューテーション検証も行わない）
- **所見を検証に渡すときは要約せず原文のまま渡す。** レンズは渡された主張しか検証しない。
  要約で論点を1つに絞ると、落とした論点は検証すらされず報告から消える。
  **論点が2つあるなら所見も2件に分けて渡す**（→ P13）

### スクリプトの骨格

```js
export const meta = {
  name: 'pr-review',
  description: 'PR の所見を観点別に出し、レンズで敵対的に検証する',
  phases: [{ title: 'Find' }, { title: 'Screen' }, { title: 'Verify' }, { title: 'Challenge' }],
}

phase('Find')
const found = (await parallel(args.finders.map(f => () =>
  agent(findPrompt(f), { phase: 'Find', label: `find:${f.key}`, schema: FINDINGS }))))
  .filter(Boolean).flatMap(r => r.findings)

// 論点が2つある所見はここで2件に割り（要約しない）、実害の無いものはレンズを回さず落とす
const items = split(found).filter(hasRealImpact)

const verified = await pipeline(items,
  // Screen: legacy を1枚だけ流す
  f => agent(legacyPrompt(f), { phase: 'Screen', label: `legacy:${f.file}`, schema: VERDICT })
         .then(v => ({ f, votes: [v] })),
  // Verify: 一次資料で「既存」が確定し、かつ実害が High 級でなければ2レンズを省く
  r => (r.votes[0].verdict === 'REFUTED' && r.votes[0].isPreExisting && r.f.claimed_severity !== 'High')
    ? r
    : parallel(['reachability', 'impact'].map(lens => () =>
        agent(lensPrompt(lens, r.f), { phase: 'Verify', label: `${lens}:${r.f.file}`, schema: VERDICT })))
        .then(vs => ({ ...r, votes: r.votes.concat(vs.filter(Boolean)) })),
  // Challenge: High 候補に red、実害 High 級なのに潰されたものに green
  r => {
    const up = r.votes.filter(v => v.verdict === 'UPHELD' && !v.reservation).length
    if (up === 3) return agent(redPrompt(r.f), { phase: 'Challenge', label: `red:${r.f.file}`, schema: VERDICT })
      .then(v => ({ ...r, challenge: { kind: 'red', v } }))
    if (up <= 1 && r.f.claimed_severity === 'High') return agent(greenPrompt(r.f), { phase: 'Challenge', label: `green:${r.f.file}`, schema: VERDICT })
      .then(v => ({ ...r, challenge: { kind: 'green', v } }))
    return r
  },
)

return verified.filter(Boolean)
```

- `VERDICT` スキーマには `verdict` / `reason` / **`basis`（何を読んで判断したか）** / **`reservation`（検証できなかった前提。無ければ空文字）** / `isPreExisting` を必ず持たせる。
  `basis` は票の独立性の判定に、`reservation` は留保票を弾くのに使う。どちらも後から復元できない
- `FINDINGS` には `claimed_severity` と `user_impact` を持たせる。
  前者は Screen の省略判定と green の対象選定に、後者は `hasRealImpact()` の判定に要る
- `split()` / `dedupe()` / `hasRealImpact()` はスクリプト内の素の JS で書く。エージェントにやらせない

## ⑤ 棚卸し（⑥を書く前に必ず）

Workflow の戻り値で全件が揃っているので回収漏れは起きない。だが**検証の中身が埋まっているかは別**。
⑥を書き始める前に、**Medium 以上に置く所見を1件ずつ**次の観点で点検する。

レンズは渡された主張を検証するだけで、その主張が**乗っている前提**は問わないことがある（→ P14）。

- この所見が成立する前提は何か。その前提を**誰がどう確認したか**を1行で言えるか
- レンズの回答に「〜は検証不能」「〜は確認できていない」という但し書き（`reservation`）が付いていないか
- 「この操作ができる／できない」を含むなら、それを決めている **default 値**を読んだか
- 「変更前と変わった」を含むなら、**変更前が正しかったか**を確認したか
- **REFUTED が揃った所見は、3枚の `basis` が実質同じか**。同じなら票の独立性が無いのでフラグを立てる

埋まっていなければ**自分で埋めてから**優先度を決める。grep 1回・別リポジトリを5分読むだけで
埋まる前提を放置したまま報告すると、ユーザーの一言で格下げになる。

検証メタに以下の形で書く（**数が合わなければ⑥を出さない**）:

```
所見 N件（観点別 M件 + sweep K件）
→ 実害なしで落とした Z件 → 検証対象 N-Z 件
→ legacy 全 N-Z 件 / reachability・impact S件（既存確定で省略）
→ red H件 / green G件 / 自分で追加確認 X件
```

## ⑥ 統合報告

**読み手が最初の数行で「何を直すべきか」を掴めることが最優先。** 検証の途中経過を本文に並べない。

**報告は最後に1回、全部入りで出す。** 遅れて所見が届いたら、**報告済みの本文を差分で直すのではなく、
番号を振り直した完全版を1メッセージで出し直す**
（読み手は「#3 と #7 を直して」と番号で指示する。番号が前のメッセージに散っていると参照できない）。

要点は5つ:

1. **載せるのは High / 要確認 / Medium の3つだけ。** Low 相当・「直さない」相当（実害なし・既存負債・些末・好み）は
   **本文に一切書かない。** 件数だけ検証メタに1行で残す。実害のある所見が埋もれるのが一番の害で、
   「見たが対応不要と判断した」の記録は聞かれてから出せば足りる
2. **全項目に通し番号 `#N` を振る**（High から Medium まで通し）。**セクションごとに 1 から振り直さない**
3. **各項目を「性質 / 新規・既存 / ユーザー影響 / 対策」の4点セットで書く**。所見の文章をそのまま貼らない。
   「性質」でこれが何の問題か（バグ/規約違反/設計/リリース手順/仕様不一致…）を分類し、
   「ユーザー影響」は必ず**ユーザーから見て何が起きるか**で書く（「型が嘘」ではなく「保存されていないのに成功トーストが出る」）
4. **「新規/既存」は legacy レンズの結論をそのまま1行にする**（この PR で入ったのか、前からあったのか）。
   読み手が最初に知りたいのは「自分がこの PR で壊したのか」で、対応の要否がここで決まる。
   **全項目に付ける**。既存と判定したなら**同型の既存実装を1つ示す**
5. **性質がバグ（潜在バグ含む）の項目には「原因」を1行足して5点セットにする**（性質 / 新規・既存 / **原因** / ユーザー影響 / 対策）。
   原因は**なぜそうなるかの機構**を、症状の言い換えにならないように書く（「タイトルが誤る」ではなく
   「Helmet が全インスタンスを再集計し、最後にマウントされた画面の title を採用するため」）。
   これが無いと読み手が対策の妥当性を判断できず、誤った直し方を選ぶ。バグ以外（規約違反・設計・確認事項）には付けない

```
## PR #<番号> レビュー結果（検証済み・修正なし）

**結論**: <1〜2行。実害のあるバグは何件か。High が何件、要確認が何件か>

---

### 🔴 High — マージ前に必ず直す

**#1　<一行で問題を言い切る>**　`<file:line>` or `<関連PR等>`
- **性質**: <バグ / リリース手順 / 規約違反 / 仕様不一致 / 設計 / …>
- **新規/既存**: <この PR で入った（新規退行） / 前からある既存負債（同型の既存実装を1つ挙げる）>
- **原因**: <バグのときのみ。なぜそうなるかの機構を1行。症状の言い換えにしない>
- **ユーザー影響**: <ユーザーの操作 → 実際に起きること>
- **対策**: <具体的にどう直すか。有害な修正案があれば ⚠️ で警告を添える>

### 🟠 要確認 — マージ前に必ず確かめる
（実害は High 級だが確信度が CONFIRMED に届かないもの。同じ形式に加えて必須で1行）
- **確定方法**: <何を測れば確定するか。例: 「stg にデプロイしてログの payload 種別を1回見れば確定する」>

### 🟡 Medium — この PR で直したい
（同じ形式で #N, …）

---

### 📋 検証メタ

- 所見 N件 → 取り下げ（REFUTED）X件 / 重大度を下げた（DOWNGRADED）Y件（一覧は聞かれたら出す）
- **本文に載せなかったもの: 実害なしで落とした Z件 / 既存負債 W件（一覧は聞かれたら出す）** ← 1行に収める
- **検証カバレッジを数で書く**（⑤の形式をそのまま）。**数が合わない状態で出さない**
- green が復権させた所見があれば件数と、なぜ最初に潰れたかを1行
- **票の独立性が無かった所見**（3枚の `basis` が同一）があれば件数を明記する
- 誤りの傾向を1行で正直に書く（例: 「既存パターンを新規退行と誤認したのが最多」）
- 検証中に棄却した捏造所見があれば明記する（どのレンズが何件、どう確認して棄却したか）
- フロー逸脱があれば1行（例: 規約担当が独断で lint を実行した）
- worktree: <パス>。手動作成のため自動削除されない。**「レビュー完了」と言ってもらえれば⑦で削除する**と添える
```

### 優先度の付け方

優先度は**実害の大きさ**で決め、**確信度はセクションを分ける**のに使う。

| | 基準 |
|---|---|
| 🔴 **High** | マージ/リリースすると実際に壊れる。コード修正が要らない手順の問題もここ（ただし下記「所見にしないもの」を除く）。**CONFIRMED（3レンズ全票 UPHELD + red 通過）のものだけ** |
| 🟠 **要確認** | **実害は High 級だが確信度が PLAUSIBLE / SPLIT**。直すかどうかの前に「確かめる」が行動になるもの。**「確定方法」を必ず書く** |
| 🟡 **Medium** | 今は壊れていないが、この PR の責任範囲で直すべき。潜在バグ・明文規約違反・仕様との不一致。**ここにもユーザー影響を書けることが条件** |
| （載せない） | 実害なし / 保守性・好み・表記 / 既存負債 / 別リポジトリ起因 / 申告済みのスコープ外変更。**検証メタの件数のみ** |

- **High と要確認を混ぜない。** 両者は行動が違う（直す / 確かめる）ので、同じセクションにラベル違いで並べると読み手が毎回仕分け直すことになる。
  読み手は優先度だけを見て動くので、**ラベルで注記しても効かない**（→ P5）
- **確信度が足りないだけで実害が大きいものを Medium に落とさない。** それが「要確認」を作った理由（→ P14）
- **実害の無い所見を Medium に押し込んで延命しない。** 落とすものは落とす。
  全部落ちて**実害のある所見が0件になったら、そう言い切る**（件数を作るために格上げしない）
  ただし**明文規約違反は実害が無くても Medium に残す**（後で効いてくるうえ、根拠が条文で一意に決まる）
- 既存負債は本文に載せないが、**実害があるものは載せる。** そのとき「新規/既存」欄に既存と書き、同型の既存実装を1つ示す。
  「既存だから」は**報告しない理由にならず、優先度を下げる理由でもない**（読み手が「自分が壊したのか」を判断するための情報）

### 所見にしないもの（Find で出させない。出てきたらレンズを回さずに落とす）

- **ユーザー影響を書けないもの。** 「型が嘘」「保守性が下がる」「命名が揺れている」「この書き方のほうが綺麗」は、
  正しくても落とす。判定は `user_impact` が**ユーザーの操作 → 起きること**の形で書けているかで行う
- **PR 本文・仕様書・ドキュメントの記載についての指摘。** PR 本文の書き方・不足、参照している番号の誤り、
  仕様書と実装の記述差、コメントや README の古さは所見にしない（聞かれたら答える程度）。
  レビューの対象は**動くコードの挙動**。
  - ただし**実装が仕様どおりに動かない**のは別で、これは実害のあるバグとして扱う。落とすのは「書いてあることの指摘」で、
    「書いてあるとおりに動かない」は落とさない
- **リポジトリ固有の除外ルール**が `references.local/` にあれば、それも同じ扱いで落とす
  （リリース順序など、チームの運用で成立しない指摘は毎回同じものが上がってくる）

## ⑦ 後片付け（worktree の削除）

**ユーザーが「レビュー完了」「もう確認した」「片付けて」等の完了指示を出したら、③で作った worktree を削除する。**

- **⑥の報告直後に勝手に消さない。** ユーザーは報告を読んだあとその worktree で実際に画面を触って確認する。完了指示を待つ
- 手順:

```bash
git -C <worktree パス> status --short          # 1. clean か確認
# 2. その worktree の中にいるなら ExitWorktree(action: "keep") で元ディレクトリへ戻る
git -C <repo> worktree remove <worktree パス>  # 3. 削除
git -C <repo> worktree list                    # 4. 消えたことを確認
```

- **`git status` が dirty なら消さない。** 差分の中身を見せて、消していいかユーザーに確認する。ユーザーが手元で試した変更が残っている可能性がある
- **`--force` は使わない。** remove が失敗したら理由をそのまま見せて判断を仰ぐ
- **`worktree remove` はブランチを消さない。** ③で `-b` を付けて作ったローカルブランチが残る。消すかどうかは**必ず確認してから**（`git branch -d '<branch>'`）

## 注意

- **判断はすべて読み取りで行う。** コードを修正しない。lint / test / ビルド（＝所見を出すための実行）は一切しない。判断に使うのは Read / Grep / `git`（`show` / `diff` / `log`）/ `gh` だけ
  - **例外は③の環境準備だけ**（依存インストール等）。これはレビューのための実行ではなく、レビュー後にユーザーがその worktree で画面を触るための準備なので必ず実行する。読み取り専用を理由に飛ばさない
- 終了時に `git status` が clean であることを確認する（worktree の追加以外に何も変えていないこと）
- **取り下げた所見を本文に列挙しない**。件数だけ添える。実害があるものが埋もれる
- **確信度・新規/既存・重大度を多列テーブルに詰め込まない**。⑥の「優先度セクション + 通し番号 + 4点セット」の箇条書きが一番読める
- **1項目に根拠の引用や条文を詰め込まない。** 4行（バグなら「原因」を足して5行）に収め、条文やコード引用は最小限で添える。詳細は聞かれてから出す
- **自分の判断で REFUTED を握り潰さない**。迷うものは残して人に見せる
- 過剰検出があったら件数で正直に書く。ただし短く（自己批判で直すべきものを埋もれさせない）
- **このファイルは公開リポジトリに入る。** 社内の識別子・テーブル名・prop 名・運用ルールを書かない。
  それらは `references.local/` に置く
