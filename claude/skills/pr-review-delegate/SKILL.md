# PR のレビューを別セッションに任せる

レビューそのものは向こうのセッションの `/pr-review` がやる。ここでやるのは、**正しい場所で起動して、見守って、知らせる**ことだけ。

## 決まりごと

- **向こうのセッションに文字やキーを送り込まない**（`pane send-text`・`pane send-keys`・`agent send`、起動後の `pane run`）。承認ボタンを押すのも同じ。承認や質問への答えは、指示者が向こうのタブで直接する
- **後片付けは向こうのセッションがやる。** worktree の削除は、向こうのセッションが「レビュー完了」を受けてからやる
  - 指示者がこちらに「レビュー完了」と言ったら、向こうが `idle` なのを確かめて `herdr pane run <pane_id> "レビュー完了"` で伝え、worktree が消えたのを `ls` で確かめて報告する（指示者に頼まれた、この 1 文だけは送ってよい）
  - タブを閉じるのは、指示者に頼まれたときだけ
- タブは `--no-focus` で作り、指示者の見ている画面を奪わない
- ID（`w1:t5S` など）は毎回取り直す。前に見た ID を使い回さない

## 手順

### 1. herdr の中か確かめる

`echo $HERDR_ENV` が `1` でなければ herdr の外なので、そう伝えて止める。

### 2. 対象のリポジトリを決める

1. `gh pr view <PR URL> --json number,title,body,headRefName,baseRefName` で PR の情報を取る
2. 手元のクローンを探す。`~/Documents/src` の下で、`git remote get-url origin` が PR のリポジトリと一致するディレクトリを使う（ディレクトリ名がリポジトリ名と違う、改名前の名前のままのことがある）
3. 見つからない・複数あるときは指示者に聞く

### 2.5. PR が複数なら、セッションの分け方を決める

- **関連する PR は 1 つのセッションにまとめる。** フロントとバックのセットは必ずまとめる（繋ぎ目の API の契約・文言の受け渡しは、両方を見ないとレビューできない）
  - 関連の目安: 同じ Issue を参照している、本文で互いを参照している、ブランチ名がそろっている、片方の変更をもう片方が使う
- **関連しない PR は、PR ごとに別のセッションを起動する**（3〜5 を PR の数だけ回す）
- どちらか迷うときは、根拠を添えて指示者に聞く

まとめるとき:
- 起動するディレクトリは、変更の起点になる側（フロントとバックならバック、呼び出す側と呼ばれる側なら呼ばれる側）のリポジトリのルートにし、他のリポジトリは `--add-dir` で足す
- 起動の指示に、すべての PR URL と「関連 PR なので 1 本の統合報告にまとめ、PR 間の繋ぎ目も観点に入れる」ことを書く

### 3. タブを作って起動する

1. `herdr workspace list` のラベルから、リポジトリに合うワークスペースを選ぶ。合うものが無ければ指示者に聞く
2. `herdr tab create --workspace <ID> --label <タブ名> --cwd <リポジトリの絶対パス> --no-focus`。返ってきた `result.root_pane.pane_id` を控える
   - タブ名は PR の中身を日本語 6 文字以内に要約する（例: `ログイン文言`）。PR 番号は使わない（サイドバーで何のレビューか分からない）
3. `herdr pane run <pane_id> "claude -n <タブ名> '/pr-review <PR URL>'"`
   - `-n` でセッションの表示名をタブ名とそろえる（タブを閉じたあとも `/resume` の一覧でどのレビューか分かる）
   - `--remote-control` は付けない
   - まとめるときは `claude -n <タブ名> '/pr-review <PR URL> <PR URL> 関連 PR なので…' --add-dir <他のリポジトリの絶対パス> ...`
   - **プロンプトは `--add-dir` より前に置く。** `--add-dir` は値を複数取るので、後ろに置いたプロンプトまでディレクトリとして読まれ、空のプロンプトで立ち上がる
   - 指示者から追加の指示（「重くていいから全部見て」など）があれば、PR URL の後ろに続けて書く

### 4. 起動を確かめて報告する

`herdr wait agent-status <pane_id> --status working --timeout 60000` で動き始めたのを確かめる。

**スキルが起動したかまで確かめる**（Claude が立ち上がっただけで、入力欄が空のまま・プロンプトがただの文章として扱われている、ということがある）。1〜2 分おいて `herdr agent read <pane_id> --source recent --lines 200` で読み、次がそろっていれば起動している:
- 入力欄に `❯ /pr-review <PR URL>…` が載っている
- `pr-review` の手順どおり、PR の情報の取得 → `references.local/` の読み込み → 規模の見積もり → worktree の作成、と進んでいる

そろっていなければ、画面の内容を伝えて指示者の判断を待つ。

報告: ワークスペース名・タブ名・ディレクトリ・PR のタイトルと URL。

**起動・承認待ち・結果、どの報告でも PR の URL を添える**（指示者がそのまま PR を開けるように）。

### 5. 見守る

状態が `blocked`（承認・入力待ち）か `done` / `idle`（手を止めた）になるまで、バックグラウンドで待つ。`run_in_background` で次を流し、終わったら通知で戻ってくる。

```bash
while :; do
  s=$(herdr agent get <pane_id> | grep -o '"agent_status":"[a-z]*"' | cut -d'"' -f4)
  case "$s" in blocked|done|idle) echo "$s"; break ;; esac
  sleep 30
done
```

戻ってきたら `herdr agent read <pane_id> --source recent --lines 150` で画面を読み、状態ごとに次のようにする。

| 状態 | やること |
| --- | --- |
| `blocked` | 何の承認・質問で止まっているかを、向こうの画面の文面に即して短く伝える。「向こうのタブで答えてください」と添え、5 の待機をもう一度流す |
| `done` / `idle` で統合報告が出ている | 所見を要点だけまとめて伝える（重大度・件数・各所見の一行要約）。全文は向こうのタブにあると添える。見守りはここで終わり |
| `done` / `idle` で統合報告が無い | 途中で止まっている。最後の画面の内容（エラー・質問）を伝えて、指示者の判断を待つ |

報告のあと、「レビュー完了」と言ってもらえれば向こうに伝えて worktree を消してもらう、と添える。
