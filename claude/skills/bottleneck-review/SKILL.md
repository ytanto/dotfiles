name: bottleneck-review
description: Claude Code の過去の会話の記録から、指示者が確認・承認で作業を止めていた場面を集計し、原因をハーネスの設定（ask ルール）・モデルの聞き方・メモリの散らばりに仕分けて、直し方を提案する。「ボトルネックを振り返って」「承認待ちを分析して」「確認が多すぎないか見て」「/bottleneck-review」のように頼まれたときに使う。定期的な振り返り（週 1 回程度）を想定。確認や承認の話題に触れただけでは起動しない。
---

指示者が「承認する」「OK と返す」だけのために作業が止まっている場面を、会話の記録から数えて原因を突き止め、直し方を提案する。**提案までがこのスキルの範囲**で、設定・CLAUDE.md・メモリ・共有リポジトリを変えるのは、指示者の OK をもらってから。

## 1. 集計する

期間は既定で 7 日。前回の結果（`~/.claude/bottleneck-review/metrics-*.json`）があれば、前回の日付以降に合わせてよい。

```
python3 -I ~/.claude/skills/bottleneck-review/scripts/collect.py --days 7 --out <scratchpad>/bottleneck-review
```

標準出力に件数の要約（`metrics.json` と同じ）と、前回の結果のパスが出る。詳細は `--out` に書き出される。

| ファイル | 中身 |
|---|---|
| `harness_prompts.json` | 承認の画面が実際に出たもの。`reason` に効いたルールの出どころ（`rule:projectSettings` ならリポジトリ共有の設定）、`after_user_ok` は直前 10 分以内に会話で OK をもらっていた（二重の確認） |
| `auto_mode_rejects.json` | 設定・auto モードの判定が止めたもの。`automode-unavailable` は判定が一時的に返らなかっただけ |
| `ask_questions.json` | AskUserQuestion の質問と答え。`picked_recommended`（推奨をそのまま選んだ）、`free_text`（選択肢を選ばず書き込んだ。聞き返し・差し戻しのことが多い） |
| `prose_approvals.json` | 文章で「〜してよいですか」と聞き、短い OK で返されたもの |
| `generic_risky_commands.json` | `rm`・PR / Issue の作成など、確認ルールの対象になりがちな操作が、実際にどう扱われたか（ルールの無い場所での判定の結果と比べるため） |
| `ask_rules.json` | 記録に出てきた作業場所ごとの、リポジトリ共有・個人の `ask` ルール |
| `confirmation_memories.json` | 確認・承認に関わるメモリ（リポジトリごとに散らばっていないかを見る） |

件数が 0 のとき、または `permissionDecision` が見つからないときは、Claude Code の版で記録の形式が変わった可能性がある。生の記録を 1 件見て、スクリプトを直してからやり直す。

## 2. 仕分ける

### A. ハーネスの設定で止まっている

- `harness_prompts.json` の `reason` から、どのルールで止まったかを特定し、`ask_rules.json` でそのルールがどのファイルにあるかを確かめる
- 拒否（`user_reject`）がほぼ無く、中身が一時ファイルの後始末のような操作ばかりなら、そのルールはノイズ。`generic_risky_commands.json` で、同じ操作がルールの無い場所では auto モードの判定でどう扱われたか（そのまま通った・止められた）と並べると根拠になる
- `after_user_ok` が付いているものは、会話の確認とハーネスの確認の二重。どちらかに寄せる
- 同じリポジトリでも、本体と worktree で `ask_rules.json` の中身が違えば、古い版のまま作業しているブランチがある。develop などの取り込みを各セッションに伝える案を出す
- `auto_mode_rejects.json` のうち判定が止めたもの（`automode-blocked`・`permission-rule`）は、止めて正しかったかを確かめる。正しければ「判定は効いている」根拠として報告に使う

### B. モデルの聞き方で止まっている

グローバルの CLAUDE.md の「指示者に確認を挟む操作と挟まない操作」に照らして、質問と文章の確認を分ける。

- **聞かなくてよかった**：「聞かずに進める」側の操作を聞いている（読むだけ、手元で戻せる作業、セッション同士のメッセージなど）
- **分けすぎ**：同じ会話で数分の間に、1 つの作業の確認が続いている（「文を見せる」→「入れてよいか」など）
- **調べ不足**：`free_text` の答えが質問や反論になっている（「すでに Issue ない？」「推奨は？」など）。聞く前に調べれば済んだもの
- **本当に指示者の判断**：推奨と違う答えが選ばれたもの、仕様・費用・本番に関わるもの。ここは減らす対象にしない

推奨をそのまま選んだ割合は目安にとどめる。割合が高くても、本当に指示者の判断だった質問は除いて考える。質問の文面に出てくるスキル名や引き継ぎ書（「決まりでは毎回確認」など）から、慎重すぎる決まりの出どころをたどる。

### C. 指示がセッションをまたいで伝わっていない

`confirmation_memories.json` に同じ趣旨のメモリが複数のプロジェクトにあれば、メモリがリポジトリごとで、ほかのセッションに届いていない。全セッションで読まれるグローバルの CLAUDE.md への集約を提案する。

## 3. 報告する

前回の結果があれば、主な件数の増減を最初に一言添える。

1. **止まった回数の表**：ハーネスの承認待ち・AskUserQuestion・文章での確認・判定が止めたもの。待ち時間は中央値で語る（合計には指示者が席を外していた時間も入るので、上限として扱う）
2. **原因ごと**：根拠の件数と代表例を 2〜3 件。どのファイルのどのルール、どのスキル・メモリが原因かまで特定する
3. **直し方の案**：どこを・どう変えるか。リポジトリ共有の設定を変える案は、ほかの人の挙動も変わるので、PR で相談する形を添える

直し方を進めるときは、指示者に 1 問ずつ、ある程度まとまった粒度で聞く。

## 注意

- 出力には会話の断片（コマンド・質問・返事）が入る。scratchpad に置いたままにし、PR・Issue など外へ書くときは件数と一般化した例だけにする。コマンドの全文・顧客名・秘密に見える値は出さない
- `~/.claude/bottleneck-review/` には件数だけを残す。会話の中身は残さない
- このスキルは公開リポジトリ（dotfiles）にある。スキルとスクリプトに、会社名・リポジトリ名・プロダクト固有の値を書かない
