# 分からなくなったところを、図と画像で説明し直す

やり取りが長くなると、略語・番号・途中の訂正が積み重なり、指示者は「結局どういうことか」を見失う。文章で言い直すだけでは、同じ読みにくさが残る。そこで、いま話していることを **図・画像・表つきの 1 ファイルの HTML** にまとめ直す。

- **読み手は指示者本人。** 会話の文脈は共有しているが、細部は追えていない前提で書く
- 読み終えたときに、**結論 / なぜそうなるか / 何をすればいいか** が分かれば成功
- 出力は手元の `~/Downloads` に置き、`open` で開く。claude.ai の Artifact などには上げない（社内の画面やコードが写ることがあるため）。指示者が「共有したい」「Artifact で」と言ったときだけ、そちらにする

## Step 1: 何が分からなくなったのかを特定する

資料の中心は、**指示者がつまずいた 1 点**に置く。全部を説明し直そうとすると、また長くなる。

- 直前の指示者の質問を、言葉どおりに読む（「結局どうすればいい」「どのパターンを見ればいい」など）。それに答える資料にする
- 会話で使った**自分の呼び名**（①②、A/B 案、略語、内部の変数名）を洗い出す。資料では使わないか、最初に定義する。指示者が分からなくなる一番の原因は、自分が勝手に付けた呼び名であることが多い
- **途中で説明を訂正したこと**があれば、それも洗い出す。資料では訂正後の内容だけを書き、前の説明が誤りだったことを 1 行で明記する

## Step 2: 事実を確かめ直す

資料は、チャットの文章より長く残り、読み返される。**推測を図にしない。**

- 会話が要約されたあとは、要約に書かれた事実も「未確認」とみなし、コード・コマンド・画面で確かめ直してから載せる
- 「これまでは〜」「〜のときは〜になる」は、実装（または実行した結果）で確かめたものだけ書く
- 応答を差し替えて作った画面・手元で確かめていないことは、資料の中にそう書く

## Step 3: 構成を決める

上から読めば分かる順に並べる。**材料の無い節は作らない。**

```
ヘッダー
  見出し：いま話していることを 1 行で（「〜で起きること」「〜の違い」）
  日付、対象（リポジトリ・PR・画面など）
  結論の囲み：3 行まで。いちばん大事なことを太字に
1. 前提・用語（表）        … 話に出てくるものの違いを表で並べる
2. 図                       … 仕組み・分かれ道・流れを 1 枚で
3. 画面で見る（あれば）    … 比べたいものを左右に並べる
4. まとめ（表）            … 条件ごとの結果、前と後の比較など
5. どうすればいいか        … 次にやること。選択肢があれば表で、おすすめを付ける
6. 根拠                     … file:line・コマンド・資料のリンク
```

### 図の描き方

| 伝えたいこと | 図の形 |
|---|---|
| どの条件でどこに行き着くか | 分かれ道の図（上から下へ。行き着く先を色で分ける） |
| 前と後、A と B の違い | 左右に並べた比較 |
| 時間の順にやり取りが進む | 縦の時系列（誰が誰に何を渡すか） |
| 部品がどうつながっているか | 箱と矢印の構成図 |

- inline SVG か、HTML と CSS で描く。**外部のスクリプト（Mermaid の CDN など）は読み込まない**（オフラインで開けなくなる）
- 箱は 12 個まで。超えるなら図を分ける
- 色だけで区別しない。凡例と、箱の中の文字（「エラー」「提案が出る」など）を添える
- **確かめたつながりだけを描く。** 推測で矢印を足さない
- いちばん伝えたい行き着く先（エラーなど）は、太い枠と色で目立たせ、その横に短い注記を置く
- 色は CSS 変数で塗り、ダークモードでも読めるようにする（ひな形の `.flow` の書き方を使う）

### 画像

- 会話の中ですでに撮った画像があれば、それを使う。新しく撮るなら Playwright で撮る（ビューポート 1440×900、`fullPage` は使わない）
- 比べたいものは左右に並べ、見出しに「提案が出る」「エラー」のような札を付ける
- 注目してほしいところには緑の枠と番号を重ね、画像の直後に同じ番号の説明を置く。枠の位置は目分量で決めず、要素の座標を測って % にする
- 画像が多いときは、長辺 1200px の JPEG に縮める（`ffmpeg -i <入力> -vf scale=1200:-1 -q:v 5 <出力>.jpg`）。`sips` の画質指定は効かないことがある
- 画像は押すと拡大できるようにする（ひな形に入っている）
- 秘匿値（トークン・パスワード）や実在の人の情報が写っていないかを目で見る

### 書き方

- 1 段落 3 行まで。長くなるなら表か箇条書きにする
- 言い切る。「〜と思われる」で終わらせない。確かめていないことは「未確認」と書く
- 会話で使った自分の呼び名（①②、案 A など）は、定義してから使う
- 前の説明を訂正するときは、何がどう違ったかを 1 行で書く

## Step 4: 組み立てる

1. 素材フォルダをセッションの scratchpad に作り、`assets/template.html` を `draft.html` として写し、`shots/` に画像を置く
2. 下書きを書く。画像は `<img src="shots/xxx.jpg">` で参照する
3. 画像を埋め込んで 1 ファイルにする

```bash
python3 <このスキルのディレクトリ>/scripts/inline_images.py <素材フォルダ>/draft.html ~/Downloads/<話題>_説明.html
```

- ファイル名は話題が分かる日本語でよい（例: `件数が多い日のエラー_説明.html`）
- 3 MB を超えたら、画像を縮めるか枚数を減らす

## Step 5: 確かめる

出力先を手元の HTTP サーバーで配信し（`python3 -m http.server <ポート> --bind 127.0.0.1 --directory <写しを置いたディレクトリ>` を `run_in_background` で立てる）、Playwright で開いて次を確かめる。`file://` は Playwright から開けないことがある。

- 幅 1280px と 390px で、ページが横にはみ出していない（`document.documentElement.scrollWidth <= innerWidth`）。はみ出すのはたいてい長いファイルのパスで、ひな形の `code { overflow-wrap: anywhere; }` で折り返す。表と図は横スクロールの枠に入れる
- 画像がすべて表示されている（`naturalWidth > 0`）
- 枠の番号と、直後の説明の番号がそろっている
- 図と画像のあたりをスクリーンショットで撮り、自分の目で見る（矢印と文字の重なり、枠が狙った要素を囲んでいるか）。ダークモード（`page.emulateMedia({ colorScheme: 'dark' })`）でも 1 回見る

確かめ終わったら HTTP サーバーを止める。

## Step 6: 渡す

- `open <HTML のパス>` で開く
- チャットには、HTML のパスと、資料の構成を 1 行ずつ、前の説明を訂正したならそのことだけを書く。資料の中身をチャットに写さない（同じ長さの文章に戻ってしまう）
- 次に頼まれそうなこと（投稿文を作る、直す、など）があれば候補を出す

## やってはいけないこと

- 会話の文章を写して並べ直すだけにする（読みにくさがそのまま残る）
- 確かめていないつながりを図に描く・推測で「これまでは〜」と書く
- 自分が付けた呼び名を、定義せずに資料で使う
- 外部のスクリプトや画像を読み込む（1 ファイルで完結しなくなる）
- 頼まれていないのに Artifact や外部のサービスに上げる
